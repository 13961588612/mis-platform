# 百购问数 Skills 使用指南（MIS 平台版）

> 适用：MIS 平台的**百购分析智能体（Worker）**，经 `iqd__ask` 工具访问 mis-iqd，由 iqd 转交 WrenAI。
> 本指南解决"这 8 个 SKILL.md 怎么接进平台、接进去要注意什么"的问题。
>
> 🔴 **本文已按新架构重写**。旧版假设"自己搭节点 + 直连 WrenAI ask API + 自己解析 SQL 做白名单校验"，
> 该假设在新架构下**三项全部不成立**（原因见 §2），照旧版做会白干。

---

## 一、先读懂这条链路

```
用户
 ↓
mis-copilot（Coordinator，只做域间分派）
 ↓  委派（TaskBrief 自包含）
百购分析智能体（Worker）← 本组 8 个 SKILL.md 在这里生效
 ↓  iqd__ask 工具（必须显式传 connection_id）
mis-iqd 编排层：范围裁定 → 生成 SQL → 行级注入 → 血缘复核 → 执行 → 脱敏 → 投影
 ↓
WrenAI → Doris
```

**本组 Skill 的位置**：Worker 的**行为规范**，指导 LLM 如何路由、如何追问槽位、如何改写出规范问句、
如何组织回答。它**不参与**取数执行。

## 二、三条被推翻的旧假设（改动根因）

| 旧做法 | 为什么不成立 | 现在怎么做 |
|--------|--------------|-----------|
| 直连 `wrenai ask API` | Skill 运行在 Worker 侧，唯一出口是 `iqd__ask` 工具；直连会绕过 ACL、脱敏、审计三层 | 一律走 `iqd__ask`，并**显式传 `connection_id`** |
| 拿回 SQL 做白名单校验 | `view=user` 下 iqd 的 `ResponseProjector` 已删除 `sql`/`sql_dialect` 键，**本层拿不到 SQL** | 越表拦截交给 iqd 侧 `in_scope` + 表级 ACL（fail-closed）；Skill 的依赖表清单降级为**上线前置检查** |
| 自己搭路由/查数/回答三个节点 | 平台已有 Coordinator–Worker 调度基座，重复造轮子且拿不到 `thread_id` 等多轮能力 | 注册为一个 Worker 智能体，8 个 Skill 挂上去；多轮靠 `thread_id` 透传 |

还有一条容易被忽略的硬约束：**Worker 的 `max_depth=1`，不可再 spawn 任何智能体**。
所以"分析到一半缺制度背景，让百购智能体去问知识问答"这条路是**断的**——
需要背景时由 Coordinator 先问知识问答，再把结论写进自包含的 TaskBrief 交给百购 Worker。

## 三、部署步骤（照着做）

| # | 动作 | 位置 | 验证方式 |
|---|------|------|----------|
| 1 | **放对目录**：八个目录放到 `packages/bgbh/` 下 | `agent/ai-platform/configs/skills/packages/bgbh/<skill_id>/SKILL.md` | 见下方🔴，**放错目录等于没部署** |
| 2 | 在新智能体的 `skills/enabled-skills.yaml` 挂 Skill | `skills.enabled: [bgbh-router, bgbh-s1-daily-report, ...]` | 技能列表接口返回这 8 个 |
| 3 | 授权取数功能码 | 该智能体 `identity/skill-permissions.yaml` + `access-control.yaml`，需含 `iqd:ask:use` | 无码时明确报权限错，而不是静默无结果 |
| 4 | 允许调用 `iqd__ask` 工具 | 该智能体 `runtime/runtime.yaml` 的 `allowed_tools` | 单条问句能出数 |
| 5 | 登记到协调者 | `configs/agents/mis-copilot/coordination.yaml` 的 `worker_ids`；`INVOKE_AGENT_WHITELIST` | Coordinator 能把百购问题派过来 |
| 6 | 在 system prompt 里钉死 `connection_id` | 该智能体 `runtime/prompts/system.md` | 见下方验证 |

> ### 🔴 第 1 步最容易放错：必须是 `packages/`，不是 `data/skills/`
>
> OpenHarness 的技能视图由 `materialize_oh_skill_view` 物化，**只扫描 `configs/skills/packages/`**，
> 不扫 custom 落盘目录 `data/skills/`。放到 custom 目录的后果：
> `skill_id` 进了启用列表，但 packages 里找不到 SKILL.md → **不进 OH 视图 → `Available Skills` 里没有
> → 模型永远不触发**。症状是"注册了、授权了、就是不生效"，且没有任何报错。
>
> **验证方法（比看日志可靠）**：部署后检查
> `agent/ai-platform/configs/.runtime/oh-skills/<百购智能体>/` 下是否出现
> `bgbh-router/`、`bgbh-s1-daily-report/`… 八个目录。
> **没出现就是没进 OH 视图。**
>
> 目录名必须严格等于 `skill_id`——OH 用父目录名作 `command_name`（粗体主名），
> 目录名写错会导致模型用错误的名字调 `skill` 工具。

**`connection_id` 的验证方法**：故意用一条只有百购库才有的表名提问，若返回的是平台默认库的表
或直接报未知表，说明 `connection_id` 没传对 —— 这是本项目最高频的静默事故。

## 四、8 个文件的职责

| 文件 | 职责 | 是否必须加载 |
|------|------|--------------|
| `bgbh-router` | 总控：**第 0 节是六条硬约束**，所有 Skill 共用；含路由仲裁、三类分流、越界拒答、结果校验；**§0.7 是改写问句的三重消费** | **必须**（首个启用，其余 Skill 的 description 已写明触发词，可独立加载） |
| `bgbh-s1` ~ `bgbh-s7` | 各主题的触发词、槽位、依赖表、问句改写模板、口径路由、回答模板、追问链 | 按 Phase 启用 |

每个业务 Skill 里两处**改动最大**的小节，务必先看：

- **依赖表（部署前置检查）** —— 原「表白名单（SQL 校验，越表即拒答）」。
  现在的用途是：① 上线前确认这些表已在 iqd 勾选 `in_scope`；② `scope_hint` 候选；③ 样本挂表依据。
  **不再是运行时校验**，因为拿不到 SQL。
- **问句改写模板（传给 `iqd__ask` 的 `question`）** —— 标题换了，价值没变反而更高：
  规范问句正是本层存在的理由。投递对象从 WrenAI 改为 `iqd__ask` 的 `question` 入参。

## 六、冒烟测试（Phase 1 只跑这 9 条）

| # | 输入 | 期望 |
|---|------|------|
| 1 | 昨天卖了多少 | 路由 S1，出昨日全店销售额 |
| 2 | 各门店排名 | 路由 S1，门店 TopN 表 |
| 3 | 会员复购率怎么样 | **先追问"哪个门店/周期"**，不直接查 |
| 4 | 库里还有几件 | 拒答（库存未覆盖） |
| 5 | 为什么销售下滑 | 分析型：先取背景数→规则话术，不下 SQL |
| 6 | 三楼昨天卖了多少 | 路由 S1，floor_name 过滤 |
| 7 | 上周客单价多少 | 路由 S2（客单价→会员口径）；Phase 1 未开 S2 → 回"该能力待上线" |
| 8 | 昨天下午三点人多吗 | 路由 S6（Phase 1 未开 → 回"该能力待上线"） |
| 9 | **connection_id 专项**：问一条只有百购库才有的表的数据 | 正常出数；**若返回其他库的表或报未知表 → 立即停，connection_id 传错了** |

**验收线**：1-2 出数正确、3 必追问、4-5 必拒答/分流、6 维度正确、7-8 降级正确、9 通过 → 9 条全过才算闭环。

## 七、上线前置检查（替代原「必须做的 4 项同步」）

原表里"Skill 侧 ↔ WrenAI 侧"直接对应的关系已不成立，中间多了 iqd 一层：

| Skill 侧 | iqd 侧落点 | 检查方式 |
|----------|-----------|----------|
| 依赖表清单 | `iqd_catalog_item.in_scope` + `iqd_scope_policy` | 逐个核是否已勾选，漏一张则取数必失败 |
| router 第 8 节全局指令 | `iqd_knowledge`（kind=instructions） | 两边文本逐条对账；**不一致时以 iqd 侧为准**并回头改 Skill |
| 各 Skill 口径路由表的术语 | `iqd_knowledge`（kind=term/metric） | 客单价/贡献率/流失周期等定义一致 |
| 问句改写模板 | `iqd_sql_pair`（树形分类） | 每题配 ≥3 种说法变体 |

> **顺序纪律**：扩 Skill 时，**先** iqd 挂表/写知识/导样本，**再**启用 Skill。反过来必失败。

## 八、常见误用（避坑）

1. **把 Skill 文件当知识库塞进 RAG** —— 错。它们是行为约束，不是检索资料。
2. **7 个 Skill 一起上** —— 错。按 Phase 开，一个不达标就单独关掉，不影响其他。
3. **改了 iqd 侧口径没改 Skill 文件** —— 错。变更顺序：《02 语义规则》→ Skill 文件 → iqd 管理面。
4. **把 DWD 明细表加进依赖表** —— 错。明细层不开放自由问数（防扫表、防绕过预计算口径）。
5. **槽位缺失时让模型"猜一个门店"** —— 错。必填槽位缺失必须追问。比报错更危险的是
   "查出一个看起来对、其实没意义的数"，用户会拿它去汇报。
6. **【新】让百购智能体去调知识问答补背景** —— 错，`max_depth=1` 会直接拒绝。走 Coordinator 注入 TaskBrief。
7. **【新】想在 Skill 里加 SQL 校验** —— 做不到，`view=user` 下 SQL 键已被删除。
   有额外安全诉求应落到 iqd 侧的 ACL / scope policy，而不是在 Skill 层写死规则。
8. **【新】忘了传 `connection_id`** —— 不报错，但查的是别的库。这是最贵的一类 bug。
