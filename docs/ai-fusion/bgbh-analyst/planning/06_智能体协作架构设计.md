# 百购问数智能体协作架构设计 v1.1

> 场景：现有智能体 = **协调者 + 问数(iqd) + 知识问答**。问题：再加"百购分析智能体"是否合适？
> v1.1 新增第 8 节：四智能体职责边界、协调者分派规则、与知识问答的协作与防重叠。

---

## 8. 加入「知识问答」后的重新判断（v1.1 核心）

### 8.1 结论：仍然加，但边界要重划

知识问答智能体的存在**不会替代**百购分析智能体，因为两者运行模式根本不同：

| 维度 | 知识问答智能体 | 百购分析智能体 |
|------|----------------|----------------|
| 输入 | 自然语言问题（无数据） | 自然语言问题（要数据） |
| 手段 | 检索文档/RAG，单轮 | 多次调用 iqd 取数 + 编排 |
| 输出 | 静态知识、定义、制度 | 基于数据的结论 + 表格 + 追问 |
| 例子 | "高端会员是怎么定义的？" | "高端会员上月流失多少人？" |
| 状态 | 无状态 | 有状态（追问链、槽位、上下文） |

**一句话区分：知识问答回答"是什么"，百购分析回答"是多少、为什么、接下来看什么"。**

### 8.2 协调者的新分派规则（按此顺序判）

```
① 是不是百购业务问题？        ─否→ 其他域/通用
② 需不需要查数？              ─否→ 知识问答智能体
     ├ "高端会员怎么定义" → 知识问答
     ├ "流失周期阈值是多少" → 知识问答
     └ "公司会员管理制度" → 知识问答
③ 需要查数 → 百购分析智能体 → iqd → WrenAI
     ├ "昨天卖了多少" → 百购分析
     ├ "哪些会员该唤醒" → 百购分析
     └ "为什么销售下滑" → 百购分析（先取数，再规则话术）
④ 跨域/超范围 → 拒答或转人工
```

### 8.3 两者协作（不是互斥，是互补）

"为什么高端会员流失多"这类分析型问题的最佳处理：

1. **百购分析**取数：高端会员流失人数、流失周期分布、去向 Top10
2. **知识问答**补背景：高端会员维护制度、历史活动记录
3. **百购分析**合并组织成回答，并在结尾标注"制度依据来自知识问答"

> 落地建议：让**百购分析智能体**做主导者，它能按需调用知识问答取背景。不要让协调者同时问两边再拼——容易拼出矛盾结论。

### 8.4 三个方案对比（推荐 A）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. 独立百购分析智能体**（推荐） | 新增一层，持 8 个 Skill | 职责清晰、iqd 可复用、后续加域照抄 | 多一跳、多一个智能体要维护 | ✅ 推荐 |
| B. 协调者持 Skill 直接调 iqd | 不新增智能体 | 少一层、上线快 | 协调者变胖；多域时它要持所有域的 Skill | ⚠️ 仅当只有百购一个域、且长期只有一个域 |
| C. 并入知识问答智能体 | 知识问答兼做百购分析 | 少一个智能体 | **运行模式冲突**：一个是无状态检索，一个是有状态编排；合并后必然一方被另一方拖累 | ❌ 不建议 |

### 8.5 与知识问答的"口径知识"防双写

两者都需要口径知识（比如"流失周期=1月≤30天"），但不算重复建设，因为**用途不同**：

- 知识问答：给**人**看的自然语言解释
- 百购分析：给 **SQL** 用的术语→列名映射（`drain_period` 取值含义）

**唯一真相源 = 《02_WrenAI语义规则》1.5 节枚举字典**。两边都从它引用，它改了两边同步改。禁止各写一份。

## 1. 结论

**加。** 但加进去的必须是**领域知识 + 编排层**，不能是"把用户的话复述一遍给 iqd"的转发层（那是纯损耗）。

**判断依据（三条，命中任一就值得加）：**

| 判据 | 百购现状 | 结论 |
|------|----------|------|
| iqd 是否要被多个业务域复用？ | 是（后续接超市/财务/其他域） | ✅ 必须把域知识从 iqd 剥离 |
| 单域是否有多主题 + 复杂槽位/口径？ | 7 个主题、必填槽位、29 张表白名单、预计算口径规则 | ✅ 知识量大，不能塞协调者 |
| 一次提问是否需要多次取数编排？ | 是（日报→门店排名→厅房下钻；流失率→清单→去向） | ✅ 需要无状态执行器 + 有状态编排者 |

**反过来说，什么情况下不加**：只有百购一个域、iqd 专用、且团队人手紧张 → 走方案 B（把 8 个 Skill 挂到 iqd 上），省一层调用。

## 2. 职责切分（关键：iqd 保持无领域知识）

| 层 | 职责 | 持有资产 | 不做什么 |
|----|------|----------|----------|
| **协调者** | 域间路由（百购/超市/财务…）、会话与权限、最终话术封装 | 域清单 | 不碰百购口径 |
| **百购分析智能体**（新增） | ①意图路由到 S1~S7 ②必填槽位追问 ③口径术语约束 ④多轮取数编排 ⑤结果业务校验 ⑥结论+表格+追问的回答组织 | bgbh-router + S1~S7 八个 Skill；《02》口径与白名单 | 不直接调 wrenai、不写 SQL |
| **iqd** | 通用取数执行器：接规范问句 → 调 wrenai → 返回结构化结果 | 无领域知识（仅 wrenai 连接、缓存、重试） | 不做业务判断、不认百购术语 |
| **WrenAI** | Text-to-SQL、建模、样本、Instructions | 百购 project 的建模/样本/术语 | — |

> 一句话：**iqd 是"手"，百购分析智能体是"脑"，协调者是"分诊台"。**

## 3. 接口契约（落地时先定这个，再写代码）

### 3.1 百购分析智能体 → iqd

```json
{
  "trace_id": "bg-20261013-001",
  "skill_id": "bgbh-s5-member-drain",
  "question": "【S5】快照日2026-10-12 八佰伴嘉兴店 高端会员各流失周期流失人数和流失率",
  "constraints": {
    "wrenai_project": "bgbh_member",
    "table_whitelist": ["ads_csmr_store_drain_analysis_d_df", "..."],
    "default_date": "2026-10-12"
  },
  "options": { "max_retry": 1, "return_sql": true }
}
```

### 3.2 iqd → 百购分析智能体

```json
{
  "trace_id": "bg-20261013-001",
  "status": "success",
  "sql": "SELECT ...",
  "tables_used": ["ads_csmr_store_drain_analysis_d_df"],
  "columns": ["drain_period", "drain_cnt"],
  "rows": [[...]],
  "row_count": 12,
  "execution_ms": 830,
  "error": null
}
```

**校验分工**：
- **iqd 侧**：表白名单硬校验（越表直接拒，不执行）、SQL 执行异常重试 1 次。
- **百购侧**：空结果降级重问、量级异常标注、业务口径合理性（如流失率为负必错）。

## 4. iqd 需要的改造（3 项，不多）

| # | 改造 | 说明 |
|---|------|------|
| 1 | 支持 `constraints.table_whitelist` | 拿到 wrenai 返回 SQL 后提取表名，越界即拒（2 行代码） |
| 2 | 支持 `wrenai_project` 传参 | 多域建模隔离时指定用哪个 project（百购侧决定） |
| 3 | 按 (question + project) 缓存 SQL | 同一问句重复出现（追问链中常见）直接命中，省一次 LLM |

**iqd 不需要改的**：不要往 iqd 里加百购术语、不要加槽位逻辑、不要加回答模板——这些全在 Skill 里。

## 6. 三个必须避开的坑

1. **转发层反模式**：百购智能体只把用户原话转给 iqd，自己不做事 → 多一跳延迟、多一次失真。**判据：如果百购智能体的输出只是输入原样，就是错的。**
2. **领域知识双写**：百购术语既写在 Skill 里、又写进 iqd 的 prompt → 改口径时两边打架。**唯一真相源在 Skill。**
3. **协调者越权**：协调者直接判断"这是流失问题"并调 iqd → 域知识泄漏到协调者，后续加域就炸。**协调者只认"哪个域"，不认"哪个主题"。**

## 9. 双通道设计：协调者什么时候可以直连 iqd（v1.1 新增）

### 9.1 结论：可以直连，但要作为"快通道"而非默认通道

**直连的真实收益**：省掉百购分析智能体的一次 LLM 调用（改写 + 组织），约省 1~3 秒、省一轮 token。
**直连的真实代价**：丢掉四件事——槽位追问、口径二次确认、回答组织（结论+追问建议）、业务异常校验。

所以判断标准不是"能不能直连"，而是**"丢了这四件事会不会出事"**。

### 9.2 准入清单（五条全中才走快通道）

| # | 条件 | 反例（必须走全通道） |
|---|------|------------------|
| 1 | 槽位齐全（时间 + 门店/品牌明确，无需追问） | "会员复购率怎么样"（缺门店、缺周期） |
| 2 | 单指标、单步，不需要多次取数编排 | "各门店排名，再看第一名的厅房" |
| 3 | 不涉及考核口径与敏感数据 | 流失考核、会员个人数据（**硬性走全通道**） |
| 4 | 非分析型（不含为什么/怎么办/建议） | "为什么销售下滑" |
| 5 | 收敛在 1~2 张已知表 | 需跨域 join 的复杂问 |

**首批建议只放 S1（经营日报）的简单问法走快通道**——口径最稳、表最少、无敏感数据。
**S5（流失/考核）永远禁止走快通道**——考核数字口径零容忍。

### 9.3 三个必须装的护栏（缺一不可）

1. **iqd 必须带 table_whitelist**：百购分析不在场，没人做越表拦截 → 白名单校验必须在 iqd 硬生效。
2. **WrenAI 侧必须已配好 Instructions + 业务术语**：术语→列的映射本由百购分析做，快通道下只能靠语义层承担。这正是《02》1.2 表描述 + 1.5 枚举字典 + 第4节 Instructions 的价值——**它们让快通道成为可能**。
3. **required 槽位缺失时 iqd 必须回抛，禁止默认填充**：最大的风险不是报错，而是**"查出一个看起来对、其实没意义的数"**。例：问"会员复购率"没给门店，iqd 若默认查全店，用户会拿这个数去汇报。这条必须硬编码在 iqd。

### 9.4 更优雅的做法：让 iqd 自己"升级"，别让协调者变胖

协调者要判断快慢，就得懂"什么算简单"——这又把域知识推回协调者。折中方案：

```
协调者：只做粗粒度分域（百购 → 交给百购分析，或按规则直投 iqd）
iqd：接单后发现 ①槽位缺失 ②需多步 ③命中敏感口径 → 返回 status: need_upgrade
协调者：收到 need_upgrade → 转交百购分析智能体
```

**把判断放在离数据最近的一层**，协调者保持"简单但可靠"。
