### 1.1 原始需求复述

在 MIS 知识库平台内，建设一套**由 MIS 自己持有**的企业术语同义词表，并在**检索发生之前**用它把用户问句里的缩写、内部代号、别名扩展成同组词再去召回，以解决「文档里写的是 A 说法、用户问的是 B 说法，向量语义又兜不住」导致的召回缺失。词表要有管理界面（增删改查 + 批量导入）、要有全局开关、要能在命中测试页看到扩展轨迹并可临时关闭做对比，并且**绝不能污染用户的原始问题**。

### 1.2 必须遵循的既定产品决策（源自文档 D1，本 PRD 不推翻）

| # | 既定决策 | 本 PRD 的落实位置 |

| 2 | **检索前在 `mis-kb` 扩展查询**，再调 `KnowledgeEnginePort.retrieve` | WD-06；对 noop/mock 一视同仁 |
| 3 | 一期范围 = **平台全局词表**，库级覆盖不做 | §3 P2 WD-20 |
| 4 | **默认开启**，全局开关可关；命中测试可**单次临时关闭**以便对比 | WD-07 / WD-11 / §5.3 |
| 5 | RAGFlow 原生 `synonym.json` / Redis 词表**仅运维可选补充**，非产品主路径 | WD-18（D-ops）/ §8 Q9 |

## 2. 产品定义

### 2.1 产品目标（三个正交目标）

| # | 目标 | 一句话说明 | 衡量方式 |
|---|---|---|---|
| **G1 召回覆盖** | 让向量语义覆盖不到的**企业缩写、内部系统代号、双向别名**在检索侧可命中 | 向量召回擅长「说法相近」，但对「OKR ↔ 目标与关键结果」这种**语料里从未共现过的映射**无能为力；这类词恰恰是企业知识库的高频提问入口 | 配置词条后，仅含一侧表述的文档可被另一侧问句召回（命中测试可复现） |
| **G2 自助可运营** | 知识管理员在 MIS 内自助维护词表，**不进引擎控制台**，全程可搜索、可批量、可审计、可一键关停 | 词表是业务资产不是运维配置；让业务方去改引擎里的 JSON 文件，等于把资产托管给一个没有权限、没有日志、升级还会丢的地方 | 管理员可独立完成「新增一组词 → 命中测试验证 → 生效」闭环，无需研发或运维介入 |
| **G3 行为透明且无副作用** | 扩展过程对**管理员完全可见**（轨迹 + 可临时关闭对比），对**终端用户与问答记录完全无痕**（原问题保真） | 查询改写是「系统偷偷改了用户的话」，不可见就不可调；同时扩展词只是检索手段，落进问答记录和 LLM 输入就会污染答案口吻与运营口径 | 命中测试可见完整轨迹；关闭开关后行为与扩展前逐字一致；问答落库与 LLM 输入均为用户原问题 |

### 2.2 用户故事

| # | 角色 | 用户故事 | 关键诉求 |
|---|---|---|---|
| **US-1** | 知识管理员 | As a 知识管理员, I want 在 MIS 里维护「规范词 + 一组别名」的术语组并随时搜索定位, so that 我不用去引擎控制台改文件就能修正业务侧反馈的召回缺失 | 增删改查、按规范词**或任意别名**搜索、分页 |
| **US-2** | 知识管理员 | As a 知识管理员, I want 把 HR/制度部门整理好的 Excel 术语表一次性导入平台, so that 我不用一条条手敲几百个缩写 | CSV/JSON 批量导入、导入前能看到会发生什么、冲突行不静默丢失 |
| **US-3** | 终端提问用户 | As a 业务员工, I want 我用平时的口头缩写提问也能查到那份用全称写的制度文件, so that 我不必先猜「系统里到底叫什么」再提问 | **完全无感知**：不额外操作、界面无新增元素、答案里不出现被塞进来的别名 |
| **US-4** | 知识管理员 | As a 知识管理员, I want 在命中测试页看到这次问句被扩展成了什么、命中了哪些术语组，并能勾一下「本次不扩展」跑第二遍做对比, so that 我能判断某条词到底是帮了忙还是引入了噪声 | 扩展轨迹可见、可 A/B、截断有提示 |
| **US-5** | 平台运维 | As a 平台运维, I want 一个全局开关能立刻把同义词扩展整体关停并确认系统回到扩展前状态，且词表变更有操作日志可追, so that 线上召回突然变差时我能在 1 分钟内排除同义词这个变量 | 全局开关、关闭即回退、变更留痕、词表规模水位可见 |

> **⚠ WD-25 的 P0/P1 分界（请勿整条延后）**
>
> 这一条容易被整体当成 P1 砍掉，那会**在 P0 里留下一个未定义行为**：WD-08 的预算规则写的是"每组最多并入 M 个别名，靠前的优先入选"——如果"靠前"没有一个确定的定义，M 生效时到底并入哪几个就变成随机的，管理员完全无法预期，也无法验收。
>
> 因此拆成两半：
>
> - **P0（属于 WD-08 的一部分）**：别名**有稳定顺序**且该顺序参与预算截断。默认顺序 = **录入顺序**（含批量粘贴与导入时的文件内顺序）。后端排序字段本波次必须就位。
> - **P1（本条 WD-25）**：让管理员**用拖拽去改**这个顺序的交互。P1 未交付时，管理员仍可通过"删掉再按想要的顺序重新添加"达到同样效果——不优雅，但不阻塞。

#### 一行怎么表达「1 个规范词 + N 个别名」

- **规范词独占第一列**，加粗，是这一组的身份标识（也是导出、日志、命中测试轨迹里的展示主名）。
- **别名列用 chip（标签块）横向排列**，最多显示 3 个，超出折叠为 `(+N)`；鼠标悬停 `(+N)` 展开浮层显示全部，**点击整行进入编辑抽屉**看完整列表。
  - 为什么不把别名全平铺：几千条词表里必然存在一组挂十几个别名的情况，平铺会让行高失控、列表变成"面条"，翻页体验直接报废。
- **「词条」列显示该组词条总数（规范词 + 别名）**，用于让管理员对"这组是不是太胖了"有直觉——这与 §7 的扩展预算（每组最多并入 M 个别名）直接相关。
- **停用组整行降对比度**，不隐藏。停用不是删除，管理员需要看得到它还在。

#### 搜索框搜什么

**搜规范词 + 搜任意别名，二者合一，不做切换。** 这是明确的产品决策：

管理员打开这个页面的**第一动机**几乎总是"业务反馈某个词搜不到 / 搜错了"，他手里握着的是**那个具体的词**（很可能是个别名，比如 `OKR`），而不是规范词（`目标与关键结果`）。如果搜索只认规范词，管理员就得先猜规范词叫什么才能搜到——这是把系统的内部结构硬塞给用户。做成两个 tab 让用户选"搜规范词/搜别名"同样荒唐：用户根本不知道自己手里那个词是哪一类。

配套要求：

- 命中的是别名时，在该行别名列中**高亮该 chip**，并在规范词下方补一行浅色小字：`命中别名：OKR`，让管理员立刻明白"我搜的词在这一组里，这组的规范词是另一个"。
- 支持部分匹配（前缀/包含），大小写不敏感，中英文一致对待。
- 搜索**在服务端执行**，与分页协同——禁止前端拉全表再本地过滤（WD-03 硬要求，对应文档 D6「管理 UI 必须分页 + 关键词搜索」）。

#### 分页

- 默认 **20 条/页**，可切 20 / 50 / 100。
- 列表默认按更新时间倒序（刚改过的在最前，符合"改完立刻要检查"的操作节奏）；规范词列支持点击切换字典序排序。

#### 录入交互细则

| 场景 | 交互 |
|---|---|
| 规范词录入 | 单行输入，必填。**规范词本身自动作为一个词条参与匹配**，管理员不需要在别名里再敲一遍（也不允许重复敲，重复输入时自动去重并轻提示） |
| 别名录入 | chip 输入框：输入后**回车**或**逗号/顿号**成 chip；点 chip 上的 `✕` 删除；**支持整段粘贴**——粘贴内容按换行、逗号、顿号、分号切分批量成 chip（管理员常直接从 Excel 单元格里复制一列过来，不支持粘贴等于逼他一个个敲） |
| 别名顺序 | 保持录入顺序，可拖拽调序。顺序有实际意义：扩展预算限制"每组最多并入 M 个别名"时，**靠前的别名优先入选**，管理员应能自己决定哪几个最重要 |
| 短词提示 | 录入长度 < 2 的词（如 `IT`）时，该 chip 显示为**灰底 + ⚠ 角标**，悬停提示：`该词过短，默认不参与自动匹配（避免误扩），仍会保存在词表中`。**不阻止保存**（WD-09） |
| 空白、大小写与全半角<br>**【U4 修订】** | 自动 trim 首尾空白；**保留管理员录入的原始写法用于展示**，但判重与匹配时按统一规则归一化。归一化口径：`trim` → `NFKC` → `toLowerCase`。<br>产品口径（**必须写进页面帮助文案**）：<br>· **「ＯＫＲ」与「OKR」视为同一个词**（全角/半角折叠），`okr` / `OKR` 亦然，不允许作为两个词条并存<br>· **「軟體」与「软件」是两个词**（繁简**不**折叠），需分别录入 |
| 删除术语组 | 二次确认弹窗，文案：`删除术语组「目标与关键结果」及其 4 个词条？删除后这些词将不再参与检索扩展，且该操作会记入操作日志。` |

#### 词条唯一性冲突（`UNIQUE(term)`）怎么提示

这是本页**最高频的出错场景**，必须做到「即时、具体、可跳转」三点：

1. **即时**：在 chip 添加的那一刻就做重复校验（**不要等到点保存**）。让管理员敲完十几个别名、点了保存才被一句"存在冲突"打回去，是最差的设计——他还得自己逐个找是哪个词冲突了。
2. **具体**：错误提示必须指名道姓说出**冲突的是哪个词、它现在属于哪个组**：
   `⚠ "OKR" 已属于术语组「关键结果法」，一个词只能属于一个组。`
   ——绝不接受 `保存失败：数据冲突` 这种把数据库约束原样甩给用户的写法。

   > **【U4 衍生边界 · 必须处理】写法不同但判为同一词时，提示要额外解释一句。**
   > U4 的归一化（全角/半角、大小写折叠）会制造一个新的困惑场景：管理员甲录入的是「ＯＫＲ」（全角），
   > 管理员乙录入「OKR」（半角）时被判冲突，乙点进那个组一看——里面写的是「ＯＫＲ」，
   > 和自己敲的**看起来就不是一个词**，于是认定系统有 bug。
   >
   > 因此当**冲突双方的原始写法不一致**时，提示必须把归一化这件事说破：
   > `⚠ "OKR" 与术语组「关键结果法」中已有的 "ＯＫＲ" 是同一个词（全角/半角、大小写视为相同），一个词只能属于一个组。`
   >
   > 写法完全一致时则不必啰嗦，沿用上面的标准文案即可。
3. **可跳转**：提示后跟一个 `[查看该组]` 链接，点击在新标签页打开那个组的编辑抽屉（或跳列表并高亮该行）。管理员的下一步动作必然是"去看看那边是怎么配的"，把这一步省掉。

冲突态下的行为：

- 冲突的 chip 以**红框**呈现并停留在输入框里（**不自动丢弃**），管理员可以就地删掉它或改成别的词。
- 保存按钮在存在冲突 chip 时**置灰**，悬停提示 `请先处理 1 个冲突词条`。
- **保存时后端必须再校验一次**（并发场景：另一个管理员刚好也在加同一个词）。此时返回的错误同样要指名道姓，且**前端不得清空用户已录入的内容**——把人辛辛苦苦敲的十几个别名一把清掉，是不可接受的。

### 4.4 批量导入

#### 4.4.1 交互流程（两段式）

```
① 选择文件            ② 预检报告（不写库）              ③ 确认导入        ④ 结果回执
┌─────────────┐      ┌───────────────────────────┐    ┌──────────┐     ┌──────────────┐
│ 拖拽或选择   │      │ 可新增   38 组             │    │          │     │ 成功 38 组   │
│ .csv / .json│ ───▶ │ 将并入已有组  6 组         │──▶ │ [确认导入]│ ──▶ │ 并入  6 组   │
│ [下载模板▾] │      │ 冲突跳过  4 行 ▸ 展开明细  │    │          │     │ 跳过  4 行   │
│  ├ CSV 模板 │      │ ─────────────────────────  │    │ [取消]    │     │[下载未导入行]│
│  └ JSON模板 │      │ 已存在的术语组：           │    └──────────┘     └──────────────┘
└─────────────┘      │   (●) 合并别名  ( ) 跳过   │
                     └───────────────────────────┘
```

**必须先看到预检报告才能提交**——导入是一次性影响几百上千条数据的操作，「选完文件直接就写库」是不可接受的黑箱。

#### 4.4.2 CSV 格式定义

| 项 | 规定 |
|---|---|
| 编码 | UTF-8；**推荐带 BOM**（与 Wave A 命中测试导出 CSV 的口径一致，Excel 打开中文不乱码） |
| 分隔符 | 半角逗号 `,` |
| 首行 | **必须是表头**，列名固定、大小写不敏感、顺序不限 |
| 列定义 | `canonical_term`（必填，规范词）、`terms`（选填，别名列表）、`remark`（选填，备注）、`status`（选填，`enabled`/`disabled`，缺省 `enabled`） |
| 一行含义 | **一行 = 一个术语组** |
| 别名分隔符 | `terms` 列内部的多个别名用**半角竖线 `\|`** 分隔 |
| 引号 | 标准 CSV 转义规则：字段含逗号/换行/引号时用双引号包裹，内部双引号翻倍 |

**为什么别名分隔符用 `|` 而不是逗号**：CSV 的字段分隔符本身就是逗号，别名再用逗号就得强制整列加引号转义。管理员是从 Excel 另存为 CSV 的，Excel 不会替他做这件事，结果就是一整列别名被撕成一堆空列。竖线在中文办公场景里几乎不会出现在术语内部，是最安全的选择。

**示例文件（可直接作为「下载 CSV 模板」的内容）：**

```csv
canonical_term,terms,remark,status
目标与关键结果,OKR|Objectives and Key Results|欧凯艾儿,集团战略管理术语,enabled
年假,带薪年休假|annual leave|年休假,HR 制度用语,enabled
星期五,周五|礼拜五,,enabled
差旅报销单,差旅单|报销单|T&E Form,"财务制度，2026 版",disabled
```

说明：

- `terms` 列**不需要重复写规范词**，系统自动把规范词并入该组词条；写了也不报错，自动去重。
- `terms` 为空表示这一组暂时只有规范词一个词条——合法，但没有扩展效果，预检报告中会以提示（非错误）标注。
- `remark` 含逗号时按标准 CSV 用双引号包裹（见示例第 4 行）。

#### 4.4.3 JSON 格式定义

| 项 | 规定 |
|---|---|
| 编码 | UTF-8（**不带 BOM**） |
| 顶层结构 | 对象（**不是**裸数组），含 `version` 与 `groups` 两个键 |
| `version` | 整数，当前固定 `1`；用于未来格式演进时的兼容判断，缺失视为 `1` |
| `groups` | 数组，**一个元素 = 一个术语组** |
| 组内字段 | `canonicalTerm`（必填，字符串）、`terms`（选填，字符串数组）、`remark`（选填）、`status`（选填，`enabled`/`disabled`，缺省 `enabled`） |

**示例文件（可直接作为「下载 JSON 模板」的内容）：**

```json
{
  "version": 1,
  "groups": [
    {
      "canonicalTerm": "目标与关键结果",
      "terms": ["OKR", "Objectives and Key Results", "欧凯艾儿"],
      "remark": "集团战略管理术语",
      "status": "enabled"
    },
    {
      "canonicalTerm": "年假",
      "terms": ["带薪年休假", "annual leave", "年休假"],
      "remark": "HR 制度用语"
    },
    {
      "canonicalTerm": "星期五",
      "terms": ["周五", "礼拜五"]
    }
  ]
}
```

**两种格式的定位**：CSV 面向"从 Excel 整理过来的存量词表"（业务部门给的就是表格），JSON 面向"系统间迁移与备份"（导出→导入的往返场景、多环境同步）。**两者语义完全等价，任一格式导入的结果必须一致**。

#### 4.4.4 导入冲突处理 —— 产品决策

> **本节是明确的产品决策，由产品经理做出，供架构师照此实现。**

**决策：分两层处理 —— 格式级错误整批拒绝；数据级冲突逐行跳过并可下载。**

| 层次 | 判定 | 处置 | 用户看到什么 |
|---|---|---|---|
| **格式级错误** | 文件无法解析（JSON 语法错误）、CSV 缺少 `canonical_term` 列、编码无法识别、超出体积/行数上限 | **整批拒绝，一行不写** | 预检阶段直接报错，连"确认导入"按钮都不出现：`文件格式不合法：缺少必需列 canonical_term。请下载模板对照修改后重新上传。` |
| **数据级错误（行级）** | 某行 `canonical_term` 为空、某个别名已属于其它术语组、同一文件内两行抢同一个词 | **该行跳过，其余照常导入** | 预检报告中单列"冲突跳过 N 行"，可展开看明细；导入后可**下载未导入行** |
| **同名规范词** | 文件中的 `canonical_term` 在平台已存在 | **默认合并**（把新别名并入已有组、去重），可在预检面板切换为"跳过" | 预检报告中单列"将并入已有组 N 组"，与"新增"分开计数 |

**为什么数据级冲突选「跳过 + 报告」而不是「整批回滚」：**

导入这个动作的真实场景是——HR 部门给了一张 400 行的术语 Excel，其中 396 行是全新的，4 行里的某个别名恰好已经被别的组占了。选整批回滚，管理员就要进入"改一行 → 重传 400 行 → 又报另一个冲突 → 再传"的循环，一张表传十几次都算顺利的；而这 4 行的冲突，本来就得他一条条人工判断该归哪组，无论如何都省不掉。**让 396 行先落地，是把管理员从机械重传里解放出来。**

**但"跳过"绝不能等于"静默丢数据"，因此以下三条是这个决策的前置条件，缺一不可（属于 WD-04 的验收项）：**

1. **必须先预检、后提交**：预检阶段不写任何数据，只出报告（可新增 X / 将并入 Y / 冲突跳过 Z / 格式提示若干），管理员**显式点击「确认导入」**才落库。
2. **冲突明细必须可见且具体**：报告中每条跳过记录都要写清 `第 27 行「OKR」已属于术语组「关键结果法」`——行号 + 冲突词 + 现属组，三样都不能少。
3. **必须提供「下载未导入行」**：把被跳过的行按**原格式**（CSV 传的就还 CSV，JSON 传的就还 JSON）导出，并**追加一列/一个字段 `skip_reason`** 说明原因。管理员改完这个小文件可以直接再传一次，形成闭环。

**规模上限（配套 §7）：**

- 单次导入 **≤ 2 MB 且 ≤ 2,000 个术语组**；超出在预检阶段拒绝，提示 `单次导入最多 2,000 个术语组，请分批上传`。
- 导入会使总词条数超过建议上限（约 1 万）时，预检报告给出**黄色提示但不拦截**（理由见 §7）。

### 4.7 权限分档（Q8 已裁决，补充导出归属）

| 动作 | 权限码 | 说明 |
|---|---|---|
| 查看列表 / 搜索 / 查看某组详情 | `kb:config:synonym:view` | 只读 |
| 新建 / 编辑 / 删除 / 启停术语组、切换全局开关 | `kb:config:synonym:edit` | 单条写 |
| **批量导入** 与 **词表导出** | `kb:config:synonym:import` | 批量读写，敏感度最高 |

> 具体码值以架构设计文档为准，本表锁定的是**产品意义上的分档边界**。

**为什么「导出」归到 `import` 而不是 `view`：**

导出会把**全量词表**一次性落到本地文件。企业术语表里往往含有未公开的内部系统代号、项目代号、组织缩写——它整体上是一份「企业内部黑话字典」，敏感度显著高于"在页面上翻几页看看"。

`view` 的授予人群应该是宽的（任何需要排查召回问题的人都该能看），而能把整份词表打包带走的人群应该是窄的。**如果把导出挂在 `view` 上，就等于把这两个人群强行合并**，结果只会是为了防导出而收紧 `view`，最后连正常的排查都做不了。挂到 `import` 上，正好让"能整批改"和"能整批拿走"是同一批人，权限模型也更好解释。

## 5. 命中测试扩展轨迹展示设计

### 5.1 展示位置

**在命中测试页现有的「本次生效参数」卡片之后、结果对比区之前，新增一块独立的「同义词扩展」卡片。**

定位理由：

- 扩展轨迹回答的问题是「**这次检索到底是怎么跑的**」，与 `effectiveParams`（本次生效参数）同类，理应相邻——管理员排查召回异常时的视线是连续的：先看参数，再看问句被改成了什么，最后才看召回了哪些片段。
- **不塞进结果列表里**：结果列表的每一项是"召回的片段"，扩展轨迹是"本次检索的元信息"，混在一起会破坏列表语义。
- **不做成折叠面板默认收起**：默认收起等于没有。这块信息本身就只有三五行，代价极小，而它是 Wave D「行为透明」目标（G3）的唯一载体。

### 5.3 「本次临时关闭」开关

| 项 | 方案 |
|---|---|
| **位置** | 调参面板中，**与现有「启用重排（rerank）」复选框同一区域，紧随其下**。它和 rerank 一样属于"本次检索的行为开关"，而非数值参数，放在一起符合既有分组逻辑 |
| **形态** | 复选框，文案：`本次不使用同义词扩展（用于对比）` |
| **默认值** | **不勾选**（即默认使用扩展，与全局默认开启保持一致） |
| **作用域** | **仅影响本次测试**，绝不写回全局开关——这与命中测试页现有的"调参只影响本次、不写回库设置"口径完全一致，页头描述里已有此承诺 |

**对比动线（这是该开关存在的全部意义，对应文档 D1-4）：**

命中测试页已有「本次结果 / 上一次结果」并排对比槽（Wave A WA-14）。管理员的标准操作是：不勾 → 跑一次 → 勾上 → 再跑一次 → 两栏并排看差异。

因此有一条**强制要求**：**「上一次结果」栏必须也显示一个精简的扩展状态徽标**（如 `已扩展 · 3 组` 或 `未扩展`）。否则两栏结果摆在一起，管理员根本分不清差异到底来自"关了同义词"还是"改了别的参数"——那这个对比就是废的。

### 5.4 对既有导出功能的补充

命中测试现有的「导出 CSV」在文件头部已包含 `测试问题` 一行。Wave D 需补充两行元信息，**位置仍在文件头部**：

架构侧提出：补两行会**改变既有 CSV 的行偏移**，需确认是否存在下游脚本按固定行号解析。**产品结论：按原方案放文件头，风险可接受。** 依据如下（均为代码核查所得，非推测）：

2. **文件名带时间戳**（`kb-hit-test-<timestamp>.csv`），落在用户自己的下载目录。要稳定消费它，脚本得先猜到文件名。
3. **格式从未作为契约对外发布**：全仓无任何 API 文档、Schema 或对接说明描述过这份 CSV 的列结构；仓库内检索 `kb-hit-test` 仅 3 处命中，全部是前端自身的组件引用与文件名拼接。
4. WA-15 在 Wave A 中是 **P2** 项，上线时间很短，且定位就是"管理员手动下载的人工诊断文件"。

因此任何消费方都只能是仓库之外某个人的私人脚本。**为一个无证据存在、且从未被承诺过的契约，去牺牲人类可读性，不划算。**

**为什么不能下沉到文件尾**：§5.4 存在的全部意义，是让接手这份文件的人**一眼看到这次检索是怎么跑的**。把"实际检索问句"埋在几十行 chunk 原文之后，等于取消了这个功能——Excel 打开默认停在第一屏，没人会先滚到底部找上下文。而 `测试问题` 已经在第一行了，把它的三个同类字段拆到文件两端，更是毫无道理。

#### 顺带把隐式契约显式化（零成本加固）

这份文件从 Wave A 起就已经是「**变长元信息前言 + 表格**」的结构（`测试问题` 那一行就是前言）。既然本波次要动它，就把规则写明，避免 Wave E 再加一行时重演同样的讨论：

> **导出文件结构约定**：文件头部为**变长**的两列元信息前言区，其后是结果表格。
> **消费方（含未来的人工与脚本）必须以"首个单元格为 `序号` 的行"定位表头，不得依赖固定行号。**
> 前言区的行数会随功能演进增加，这一点是设计意图，不是破坏性变更。

这句话写进 PRD 的成本是零，但它把一个隐式的脆弱假设变成了明示契约。
