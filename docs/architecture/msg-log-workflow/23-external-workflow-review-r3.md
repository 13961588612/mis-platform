### 事实 3：`FOR UPDATE SKIP LOCKED` 是否真的解决了并发问题？「先标记后执行」窗口，实例在 fetch 期间崩溃会怎样？

**结论：✅ 解决了「并发重复处理」，这是真问题真解法。但🟡「先标记后执行」窗口带来两个架构师没提的代价，其中一个是真缺口。**

#### 3.1 先确认它解决的是什么（✅ 对）

我推演了 r2 描述的失败序列，确认 `SKIP LOCKED` 确实挡住：

```
r2（biz_exec_lock）：轮询1轮 → INSERT 成功 → fetch →写 SUCCESS
                     轮询2轮 → PK 冲突 →见SUCCESS → return ALREADY_SUCCESS ⇒ **永久不再 fetch**
r3（SKIP LOCKED）：  轮询1轮 → 领取(打 last_sync_at) → fetch
                     轮询2轮 → 该行 last_sync_at 是新的 ⇒ WHERE 不命中 ⇒ 不会被重复领取✅
```

**我实测确认 r2 的失败序列成立**（`DistributedLockService.java:65-66` 见 `SUCCESS` 直接 return；全仓 `deleteByStatus` 调用点只有 `:70`(FAILED)、`:80`(超时RUNNING) + 3 个测试文件，**生产代码零处删SUCCESS**）。⇒ **N2 的诊断和修法都正确，这是本轮质量最高的一处修补。**

#### 3.2 🟡 代价一：崩溃窗口 = **重复 fetch**（不是丢失），且**可接受**

你问「若实例在 fetch 期间崩溃，会发生什么？」—— 我推演的完整时序：

```
t0  事务A：UPDATE last_sync_at = now()  （领取）
t1  事务A提交（行锁释放）
t2  实例崩溃 ⇦ 崩溃点在 fetch 之前或之中
t3  事务B（另一实例/下一轮）：WHERE last_sync_at < now() - 5min ⇒ **5 分钟内不命中** ⇒ 跳过
t4  5 分钟后：重新命中 ⇒ 重新 fetch ✅
```

**⇒ 结论：不丢、不重复投递、无需人工干预。** 因为「打时间戳」发生在**领取时**而不是「fetch 成功后」，所以**最坏情况是这一轮白跑，5 分钟后自动重来**。

**这个代价架构师没写出来，但结论是安全的**（至多延迟一个周期，不产生错误状态）。我建议补一句说明，因为「跳过 5 分钟」这个行为**运维排障时会怀疑成 bug**。

#### 3.3 🔴 代价二：fetch 期间的**数据一致性窗口** —— 同一行可能被并发 fetch 两次（真缺口，但危害可控）

**这才是「先标记后执行」的真正代价，架构师完全没提。**

关键在于：**`FOR UPDATE` 的行锁在事务提交时就释放了，而 `fetch()` 在事务外。** 所以：

```
实例A：领取(提交) ──── fetch(caseId) 在途 ──── 写回 applySnapshot()
实例B：                    ▲
                          └─ 若 A 的 fetch 很慢（15s 超时），而 B 这一轮恰好开始
                             且距 A 领取已 > 5min（批大时可能发生）
                             ⇒ B 也能领取同一行 ⇒ 两人同时 fetch 同一 caseId
```

**⇒ 不是「丢失」，是「同一行在极小概率下被并发 fetch 两次」。** 危害评估：

| 危害 | 是否存在 | 说明 |
|---|---|---|
| 重复触发后置任务（重复发货） | ❌ **不会** | `ext_terminal_event` 的 `UNIQUE` + `ON CONFLICT DO NOTHING RETURNING id` 在**同一事务内**判重，与 fetch 并发无关。**这是 N3 修补的额外红利 —— 它顺带兜住了N2 窗口** |
| 状态被旧快照覆盖回退 | 🟡 **可能，但已被拦** | 两个 `applySnapshot()` 交错写库。**但「终态单调性」断言在 `save()` 之前**（`19:337-341`，这条我上轮要求、这轮已落地 ✅）⇒ 终态不会被改回 `RUNNING`。剩下的风险是「`RUNNING` 被另一个 `RUNNING` 覆盖」= 无害 |
| 连接池压力 | 🟡 轻微 | 批量 fetch 时并发度可能翻倍。文档已提「15s 超时 × 批量会拖垮连接池」，但那是针对「持锁跨 HTTP」的，**没针对「并发 fetch 翻倍」** |

**⇒ 判定：🟡 建议补一条约束，不是阻断。** 建议在 `19§7` N2 专项表里加第 5 行：

| **🔴 认领窗口** | 领取事务提交后行锁即释放，`fetch()` 在事务外 ⇒ **极小概率下同一行会被两个实例并发 fetch**（当单批耗时 > 5min 保护期）。**不丢、不重复投递**（`ext_terminal_event` 同事务判重兜住）、**终态不会回退**（单调性断言兜住）；剩余代价是**外部接口调用量可能翻倍 + 连接池压力**。缓解：`batch_size` 需保证单批 `fetch` 总耗时 < 5min（`timeout_ms=15000` ⇒ **batch_size ≤ 20**），否则须调长保护期。 |
