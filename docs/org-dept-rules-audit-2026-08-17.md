### A.1 逐条判定

### A.2 规则组 1 结论摘要

**规则组 1 的"骨架"已具备且稳健**：创建组织即在事务内生成 `isRoot=1 / parentId=0` 的同名根部门（1.1、1.2 达成），且通过"服务层拒绝 + 数据库部分唯一索引"双重锁死"每组织仅一个根部门、且不得手工新建/移动为根"（1.6 达成）。

**但"命名/状态与组织强绑定"这一核心诉求尚未实现**：根部门名称仍可被 `DeptService.update` 独立修改（1.3 的"不可修改"未守卫），且修改组织名称/状态不会同步到根部门（1.4 缺失），进而"组织改状态只动顶级部门、不动子部门"的 1.5 也无从谈起。这三点是规则组 1 的主要缺口，且彼此耦合（1.5 依赖 1.4）。

## E. 规则组 2 · 2.4 明确设计建议（取消按钮 vs 保留 + 箭头下钻）

### E.1 推荐方案：**取消独立「穿透下钻」按钮，改为"箭头展开=下钻"**（契合用户诉求，改造量小）

**触发逻辑重构（`dept-tree-page.tsx` 第一列箭头）：**

```ts
function onArrowClick(node: DeptNode) {
  if (node.linkedOrgId) {
    openPierce(node);          // 链接组织的部门：箭头展开即自动下钻（复用 OrgPierceDrawer）
  } else {
    toggleExpand(node);         // 普通部门：箭头展开/折叠本地子部门树
  }
}
```

**为什么这样改是干净且低风险的：**
1. **业务约束天然互斥**：`DeptService.create` L117-119 规定"已关联组织的部门不可再创建子部门"，即 **`linkedOrgId` 非空 ⇒ 该部门必定没有本地子部门**。因此"箭头向下展开"对链接部门只有一种含义=跨组织下钻，与普通部门的"展开本地子树"不冲突，无需分支判断困惑。
2. **`OrgPierceDrawer` 组件可原样复用**：其 props（`anchorDept`/`orgs`/`open`/`onOpenChange`）与已有 `openPierce` 调用完全兼容，只需把触发源从"操作列按钮"改为"箭头"，**组件内部零改动**。面包屑钻取栈与防循环逻辑（L93-111）直接保留。
3. **去掉独立按钮后，E.1 已交付的抽屉能力不丢**，只是入口从"按钮"换成"箭头"，符合 2.4"无需单独按钮"。
4. **2.1/2.3 顺带对齐**：箭头回归"子部门展开"（G4），"任职详情"交给新增的「查看任职详情」按钮（G6），三者职责清晰、互不抢箭头。

### E.2 关于"穿透下钻按钮是否可取消"
- **可取消**。从交互与实现两端都可行（见 E.1）。若担心用户找不到入口，可保留按钮作为**冗余入口**（不改变箭头逻辑），但按 2.4 原意应移除。

### E.3 对 E.1 已交付下钻抽屉的影响与改造量
- **影响：极小**。`org-pierce-drawer.tsx` **无需修改**；改造 100% 落在 `dept-tree-page.tsx`：
  - 删除 L438-446 的独立「穿透下钻」按钮（或保留为冗余）；
  - 第一列箭头 `onClick` 由 `toggleStaffing` 改为 `onArrowClick`（含 `linkedOrgId` 分支）；
  - 引入本地 `expandedIds`（树展开集合，默认空=全折叠）以支持 2.1；
  - 原"编制面板"触发迁移到新增的「查看任职详情」按钮（G6）。
- **后端：零改动**（已有 `GET /depts/tree`、`GET /depts/pierce`、`GET /depts/{id}/staffing`）。
- **改造量估计**：前端单文件中等偏轻（~80–150 行改动），无新增 API、无迁移。

### E.4 可选增强（非必需）
- 若希望"箭头展开链接部门"时**不弹抽屉、而是内联展开**被钻取组织的部门森林，可在内存把 `fetchDeptPierce` 结果挂为该节点的 `children` 并复用同一表格渲染——但复杂度上升，且会丢失抽屉的面包屑防循环体验。**默认推荐 E.1 的"自动弹抽屉"方案**。
