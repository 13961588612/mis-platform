# 门户首页改版规划 —— 工作台为主体的左右双栏布局

> **版本**: v1.0 | **日期**: 2026-10-08
> **范围**: `frontend/mis-admin-web` 门户首页（`features/portal/portal-page.tsx`）
> **背景**: 现门户是"平铺九宫格 + 顶部统计卡片 + 应用分组卡片"，工作台内容（待办/消息）与业务模块入口混在一起，
> 用户登录后第一眼看不到"我今天要做什么"。

---

## 1. 现状问题

| 问题 | 现状 | 影响 |
|------|------|------|
| 主次不分 | 子系统九宫格占据视觉主体，与"待办/消息"平级甚至更突出 | 用户登录后先看到"有哪些系统"而非"我要处理什么" |
| 工作台分散 | 待办、消息、我发起的分散在侧边栏「工作台」与门户顶部 | 需多次跳转才能拼出"当前待办全貌" |
| 应用入口沉重 | 每个子系统一张大卡片，占满横向空间 | 门户沦为"应用启动器"，缺少运营/协作价值 |
| 统计卡片是假的 | `StatCard` 显示"—""演示占位" | 首屏有空洞感 |

---

## 2. 设计目标

1. **首屏即工作台**：登录后第一次视线落在「我的待办 / 消息」上，回答"我现在要做什么"。
2. **模块入口退居右侧**：子系统/业务模块收敛为右侧窄栏的紧凑入口，不再抢占主体。
3. **数据真实**：统计与列表接真实接口（`/tasks/stats`、`/messages/inbox`、`/workflow/instances/my`）。
4. **不新增路由**：复用现有 `/task/*`、`/system/*` 页面，门户只做"聚合视图"。

## 4. 分区详解

### 4.1 顶部概览条（工作台内）

四个数字指标，接真实接口：

| 指标 | 数据源 | 点击行为 |
|------|--------|---------|
| 待办 | `GET /tasks/stats` → `pending`（子标 `urgent` 红点） | 跳 `/task/pending` |
| 未读消息 | `GET /messages/stats` → `unread` | 跳 `/task/inbox` |
| 我发起的 | `GET /workflow/instances/my` → `total` | 跳 `/task/my-sent` |
| 本月已办 | 暂可省略或取 `tasks/stats` 的已完成（后续补） | — |

样式：一行四格，竖分隔线，数字 20px/600，标签 12px muted；紧急用 `text-destructive`。

### 4.2 我的待办（核心区块）

- 取 `/tasks/my?status=PENDING&size=5`，按 `priority desc` 排序。
- 单行：优先级徽标 + 业务标题 + 当前节点 + 截止时间（逾期红字）。
- 每行可点击 → 直接进 `ProcessShell`（`metadata.wfInstanceId`，复用 P7 已实现的跳转逻辑）。
- 右下角「查看全部 →」跳 `/task/pending`。
- 空态：`✓ 暂无待办`，弱化处理。

### 4.3 消息与通知

- 取 `/messages/inbox?size=5`，未读左侧红点。
- 单行：标题 + 时间；有 `referenceTaskId` 的显示「待办」小标签。
- 「查看全部 →」跳 `/task/inbox`。

### 4.4 我发起的（可选第三块）

- 取 `/workflow/instances/my?size=3`，显示业务号 + 状态徽标（进行中/已完成/已终止）。
- 点击 → `ProcessShell`。

> 三块可配置显示顺序/数量；首屏优先"待办"，其次"消息"，再次"我发起的"。

### 4.5 右侧「模块导航」

- **我的应用**：把现在的九宫格收敛为**竖排紧凑列表**（图标 + 名称 + hover 箭头），按 `portalGroup` 分组折叠。
- **快捷入口**：常用表单/功能直达（可为空，后续按使用频次生成）。
- **最近访问**：`recent`（现有逻辑）。

样式：右侧整体 `sticky top-4`，卡片间距 12px，图标 32px 方形。

## 10. 配色规范（白色背景 · 现代商务）

> 需求：**背景色改为白色**；整体配色现代、商务。以下为可直接落地的 token 规范。

### 10.1 现状 vs 目标

| token | 现状 | 问题 | 目标 |
|-------|------|------|------|
| `--background` | `220 14% 95.5%`（灰底） | 大面积灰底，偏"老式后台" | **`0 0% 100%`（纯白）** |
| `--card` | `0 0% 100%` | 白卡浮在灰底上 | 保持白，靠**边框 + 轻阴影**与白底区分 |
| `--border` | `220 13% 90%` | 偏灰、略重 | `220 16% 92%`（更淡，减少割裂） |
| `--muted` | `220 14% 93%` | 与目标白底对比略大 | `220 20% 96%`（更轻，做浅色分区/表头） |
| `--primary` | `243 75% 59%`（偏亮紫） | 饱和度偏高，商务感不足 | `222 65% 45%`（**深商务蓝**） |
| `--sidebar` | `214 32% 90%`（浅灰蓝） | 灰感重 | `0 0% 100%` + 右边框，或 `220 30% 98%`（极浅） |

> **关键取舍**：背景纯白后，卡片不能再靠"白卡+灰底"分层，改为**「白底 + 1px 浅边框 + 极轻阴影」**，这是现代商务后台（Linear / Vercel / Stripe Dashboard）的主流做法。

### 10.2 推荐色板（HSL，Tailwind 变量）

```css
/* 浅色主题 —— 现代商务（白底 + 深蓝主色 + 中性灰） */
--background: 0 0% 100%;          /* 纯白页面底 */
--foreground: 222 25% 15%;        /* 主文字：近黑蓝，比纯黑柔和 */
--card: 0 0% 100%;                /* 卡片同为白，靠边框/阴影分层 */
--card-foreground: 222 25% 15%;
--popover: 0 0% 100%;
--muted: 220 20% 96%;             /* 浅分区/表头/hover 底 */
--muted-foreground: 220 12% 45%;  /* 次要文字 */
--border: 220 16% 92%;            /* 淡边框 */
--input: 220 16% 90%;
--ring: 222 65% 45%;

/* 品牌主色：深商务蓝 */
--primary: 222 65% 45%;           /* #2857B8 附近 */
--primary-foreground: 0 0% 100%;
--secondary: 220 20% 96%;
--secondary-foreground: 222 25% 15%;
--accent: 220 20% 96%;
--accent-foreground: 222 25% 15%;

/* 语义色：低饱和、商务化 */
--success: 158 55% 38%;
--warning: 32 85% 45%;
--destructive: 0 62% 48%;
--info: 210 70% 45%;

/* 侧边栏（可选两种风格，见 10.3） */
--sidebar: 0 0% 100%;
--sidebar-foreground: 222 25% 18%;
--sidebar-border: 220 16% 92%;
--sidebar-accent: 220 20% 96%;
--sidebar-muted: 220 12% 48%;
```

### 10.3 侧边栏两种风格（择一）

| 风格 | 取值 | 观感 | 适用 |
|------|------|------|------|
| **A. 纯白一体**（推荐） | `--sidebar: 0 0% 100%` + 右边框 | 极简、通透，与内容区一体 | 现代商务，页面对比强 |
| B. 极浅灰 | `--sidebar: 220 30% 98%` | 轻微分区，导航与内容有界 | 信息密度高的后台 |

> 主内容区与侧边栏之间用 **1px `--border` 竖线**分隔，不用色块。

### 10.4 阴影与圆角（配合白底）

```css
/* 白底上卡片必须靠阴影/边框分层，否则"糊"在一起 */
--card-shadow: 0 1px 2px rgb(15 23 42 / 0.04), 0 1px 3px rgb(15 23 42 / 0.06);
--card-hover-shadow: 0 4px 12px -2px rgb(15 23 42 / 0.08), 0 2px 6px -2px rgb(15 23 42 / 0.05);
--radius: 0.375rem;   /* 6px，比现状 4px 略柔，仍保持商务克制 */
```

### 10.5 门户具体落地

| 区域 | 背景 | 边框/分隔 |
|------|------|----------|
| 页面底色 | `--background`（纯白） | — |
| 顶部 Header | 白 + 底边 1px `--border` | 不用阴影 |
| 工作台各区卡片 | 白 + 1px `--border` + `--card-shadow` | 区与区间距 16px |
| 概览条 | `--muted`（浅灰）圆角块 | 数字用 `--foreground`，标签 `--muted-foreground` |
| 待办行 hover | `--muted` | 行间用 `border-b border-border/60` |
| 紧急/逾期 | `--destructive` 文字 + 淡底 `destructive/10` | — |
| 右侧模块导航 | 白卡 + 边框 | 分组标题 12px `--muted-foreground` |
| 侧边栏 | 见 10.3（推荐风格 A） | 右边框 1px |

### 10.6 深色主题（保持一致）

深色不改结构，仅把 `--background` 由近黑调为**深蓝灰** `222 30% 9%`，主色提亮至 `222 75% 62%`，其余语义色同步提亮，保证白底版与深色版观感一致。

### 10.7 影响面提示

- `--background` 是**全局 token**，改白会同时影响所有后台页面（不止门户）。
- 若只想改门户：在 `portal-page` 外层用 `bg-white` 覆盖，不动全局 token（但会出现"门户白、内页灰"的不一致）。
- **建议**：直接改全局 token（一次到位，全站统一现代商务），并在改后回归截图核查表格页/表单页的对比度（表格有独立 `--table-*` 色板，需同步微调）。

### 10.8 验收

1. 页面背景为纯白，卡片靠边框+轻阴影可辨，无"灰底白卡"旧观感。
2. 主色为深商务蓝，按钮/链接/选中态统一。
3. 表格、表单、门户、侧边栏四处观感一致。
4. 深色主题切换后层级同样清晰。
5. WCAG AA：正文对比度 ≥ 4.5:1，次要文字 ≥ 3:1。

## 11. 信息架构修正：个人事务 vs 管理工作（2026-10-08）

### 问题（实测确认）

V123 把「工作台」挂成了 **system 子系统的菜单**（`app_id=1, parent_id=0`），且 4 个子项都设了
`permission` 并只授予 `role_id=1`（租户管理员）。后果：

- 普通员工（无系统管理权限）**根本看不到工作台**；
- 工作台与"业务子系统"耦合，语义错误——它是**每个登录用户的个人事务中心**。

### 修正后的三层结构

| 层 | 入口 | 可见范围 | 说明 |
|----|------|---------|------|
| ① 门户 `/portal` | 登录后默认落地页 | 全部登录用户 | 工作台主体：概览 + 待办 + 消息 + 我发起的 |
| ② 全局顶栏 | 铃铛 + 工作台按钮 | 全部页面 | 铃铛接真实待办/消息；按钮回 `/portal` |
| ③ 子系统侧栏 | 仅该子系统菜单 | 按各自权限 | `SYSTEM_NAV` **移除**「工作台」分组 |

### 关键区分

| 能力 | 性质 | 权限 |
|------|------|------|
| 我的待办 / 消息 / 我发起的 / 我审批的 | **个人事务** | **登录即可**（`permission=NULL`，数据按 `assigneeId` 隔离） |
| 流程定义 / 流程编排 | 管理工作 | `workflow:definition:view` / `edit` |
| 业务审计 / 执行监控 | 管理工作 | `taskflow:audit:view` / `taskflow:exec:manage` |

> 之前把前一类当后一类处理，是 IA 错误的根因。

### 落地改动

| 改动 | 文件 |
|------|------|
| 侧栏移除「工作台」分组 | `lib/nav/system-nav.ts` |
| 顶栏加「工作台」入口 + 铃铛接真实数据 | `components/layout/header-toolkit.tsx` |
| 个人事务菜单去权限 + 全角色授权 | `V127__taskflow_personal_vs_admin_menu.sql` |
| 导航测试断言更新 | `lib/nav/system-nav.test.ts` |

### 安全说明

`/task/*` 的 BFF 接口仍校验**数据归属**：`assigneeId`/`userId` 由 `TaskflowIdentity` 从
`LoginUser` 解析（不可越权查他人），只是不再校验"功能权限"。这符合"个人事务人人可用、但只能看自己的"原则。


### 11.1 补：工作台必须是**独立宿主应用**（否则仍寄生在系统管理壳里）

**发现的问题**：仅从侧栏移除「工作台」不够——`/task/*` 路由仍被
`resolveActiveHostAppCode(pathname, loginAppCode)` 归到登录 app（`system`），
于是点「消息/待办」后整个外壳显示「系统管理 · 管理与治理」+ 系统管理侧栏。

**修法**：把工作台提升为与 `kb / agent / iqd / finance` 平行的独立宿主应用：

| 改动 | 文件 |
|------|------|
| 新增 `TASK_NAV`（工作台侧栏：待办/消息/我发起的/我审批的） | `lib/nav/task-nav.ts`（新建） |
| `resolveActiveHostAppCode`：`/task/*` 与 `/portal` → `'task'` | `lib/nav/host-apps.ts` |
| `HOST_APP_LANDING.task = '/task/pending'` | `lib/nav/host-apps.ts` |
| `navNodes` fallback 增加 `TASK_NAV` 分支 | `components/layout/app-layout.tsx` |
| `sectionLabel` / `activeAppName` / 图标：`task` → 「工作台」+ ClipboardList | `components/layout/app-layout.tsx` |

**效果**：点「消息/待办」后，外壳显示「工作台」而非「系统管理」，侧栏为工作台导航，
与业务子系统彻底解耦。
