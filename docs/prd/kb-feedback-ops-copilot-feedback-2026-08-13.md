## 1. 背景与范围界定

### 1.1 用户诉求
用户原话：「不光是知识问答可以评价，其他比如**问数**也要能评价和处理；这个如果没考虑到还要补充产品设计」。

### 1.2 核实结论（已读代码）
copilot 体系存在**两套独立反馈机制**，原 PRD 只覆盖第一套：

| 维度 | 第一套（已规划） | 第二套（本文，用户点名的问数所在链路） |
|---|---|---|
| 入口 | MIS 知识问答页（kb-qa-page） | ai-platform H5 聊天（`MessageFeedbackBar.tsx`，所有 agent 会话助手回答后均可评价） |
| 数据 | mis-kb `kb_qa_feedback` 四维评分（accuracy/helpful/offtopic/citeError） | `message.metadata.feedback = {rating, comment, updated_at}`（Redis 权威、PG 尽力同步） |
| 提交 | 前端→BFF→mis-kb | H5 `apiPost('/sessions/{id}/feedback', {rating, comment, content})` → agent 后端 `POST /{session_id}/feedback` |
| 数据形态 | 会话级一票，Long session_id | 消息级，rating="up"/"down"，吐槽 comment 必填（≤500 字），agent session_id 为 UUID 字符串 |
| 运营视图 | 已具备（列表/详情/看板/导出/工单） | **零运营视图**（无列表/统计/处理；仅 session_store 按会话读消息） |

### 1.3 场景界定（建议）
- **倾向全部纳入**：`MessageFeedbackBar` 挂在 H5 所有 assistant 消息上，覆盖 mis-copilot 及其委派 worker（crm-assistant / mis-rag / mis-summary / mis-extract）的全部对话；用户说的「问数」是其中一种场景（mis-copilot 数据查询场景，`runtime/openharness.py` 有问数分支）。
- 运营范围 = **全部 agent 会话反馈**（点赞/吐槽+comment），不做「仅问数」的子集限制；但看板与列表需支持**按 agent 维度筛选/下钻**，以便单独看问数表现。
- 与 KB 知识问答反馈**数据模型与系统均不同**，两套运营视图分开建设（见 §4），不做数据合并。

| # | 能力 | 现状说明 | 状态 | 与「问数/会话反馈运营」需求的差距 |
|---|---|---|---|---|
| 1 | 反馈采集（点赞/吐槽+comment） | H5 每条 assistant 消息可评价；吐槽 comment 必填；rating=up/down；**可重复提交（覆盖写）** | ✅ 已具备 | 无 |
| 2 | 反馈落库 | `message.metadata.feedback`：Redis 权威、PG 尽力同步（degraded 仅告警） | ✅ 已具备 | PG 同步失败时反馈只在 Redis，运营读 PG 会漏（需接受一致性口径或补偿） |
| 3 | 会话列表（运营） | agent `GET /sessions`（分页 + agent/channel/user/keyword/time 过滤）+ MIS 会话管理页 `/agent/sessions` 已接入 | 🟡 部分具备 | **无法按「有反馈/吐槽」过滤**；列表行不显示反馈状态 |
| 4 | 会话详情回放 | agent `GET /sessions/{id}` + `GET /sessions/{id}/messages`；MIS 详情抽屉回放消息，metadata 以 JSON 展开 | 🟡 部分具备 | 反馈藏在 metadata JSON 里，**无结构化徽标**；无法从详情发起处理 |
| 5 | 反馈列表/统计 | — | ❌ 缺失 | 无按 rating/comment 的反馈列表、无点赞率/吐槽率/按 agent/趋势统计 |
| 6 | 处理闭环 | — | ❌ 缺失 | 无标记已处理/忽略、无工单、无处理人/备注/时间线 |
| 7 | 跨系统工单（agent→mis-kb KbQaTicket） | mis-kb 工单 session_id 为 **Long（KB 会话）**，agent session_id 为 **UUID 字符串**，ID 空间不互通 | ❌ 缺失 | 直接复用工单需 ID 映射层，成本高，建议 P2 |

**结论**：第二套链路「采集已通、运营为零」。本次增量核心 = 在既有 Agent 会话管理能力上补「反馈聚焦视图 + 轻量处理闭环 + 统计」。

## 4. 关键决策（含倾向性建议）

| # | 决策点 | 建议 | 理由 |
|---|---|---|---|
| D1 | 运营范围 | 全部 agent 会话反馈（含问数），看板/列表支持按 agent 过滤 | 采集器天然覆盖全部；只做问数子集会漏掉 copilot 其他场景 |
| D2 | 运营入口 | **独立于 KB 3 Tab 页**：在既有「Agent 会话管理」能力区扩展（新增「反馈」Tab 或并列页面），不并入 mis-kb 运营页 | 数据模型/系统/ID 空间均不同，硬合并会污染两套口径；Agent 侧已有会话管理页与 BFF 通道，复用成本最低 |
| D3 | 处理闭环 | P0 用**轻量标记**（已处理/已忽略 + 备注 + 操作人/时间），不接 mis-kb 工单 | 吐槽未必都需工单；跨系统工单需 ID 映射与新建存储，成本高、收益不确定 |
| D4 | 跨系统工单（agent→KbQaTicket） | P2 再做，先建 agent 侧轻量工单或映射表，再评估对接 | ID 空间不同（UUID vs Long），直接复用会破坏 mis-kb 工单约束 |
| D5 | 数据打通 | **运营读取走 agent 侧新增只读端点（PG 优先，沿用 #27–#31 模式），BFF 透传，不复制到 MIS** | 保持单一事实源；agent 链路已有 Redis/PG 降级，再复制会放大不一致；P2 可评估分析库同步 |
| D6 | 统计口径 | 与 KB 看板口径**分开展示**（名称区分「KB 问答评价」/「Agent 会话反馈」），不合并 | 四维评分 vs 二值 rating 不可直接对比 |
