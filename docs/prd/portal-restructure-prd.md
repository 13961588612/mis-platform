## 1. 产品目标

**一句话目标**：把门户从「入口跳板」升级为「**个人工作聚合台**」——用户在门户一处即可总览待办与消息，并**划入抽屉一步直达流程详情（表单内容 + 审批进度 + 审批信息）**，不再受左侧导航干扰、不再为看一条待办而整页跳转。

**3 条量化指标（P0 上线后 1 个月验收）**：

| # | 指标 | 目标值 | 口径 |
|---|---|---|---|
| 1 | 门户内一步直达率 | 从门户「待办事项/消息中心」点开详情**不离开门户壳**（以抽屉呈现）的占比 ≥ 90% | 分母=门户内列表点击次数，分子=开抽屉而非整页跳转 |
| 2 | 门户导航层级 | 门户页左侧 sidebar **不出现**（隐藏率 100%） | 仅 `/portal` 生效 |
| 3 | 六类待办可检索 | 六类子 Tab 均支持关键词搜索（搜出结果可翻页） | 逐 Tab 验收，含「我发起的/我审批的」 |

### 5.1 搜索维度（PR-04 细化）

| 子 Tab | 数据源 | 可搜字段（建议） | 现状 |
|---|---|---|---|
| 待处理 / 审批中 / 已通过 / 已驳回 | `GET /tasks/my` | `bizTitle`（标题）、`assigneeName`（处理人）、`bizType`/`bizRefId`（类型/编号）、`createdAt`/`completedAt`（时间） | ❌ 无 keyword 参数 |

> **Q3 已拍板**：搜索为**各 Tab 内独立搜索**，不做跨 Tab 全局（PR-15 全局搜索保持 P2）。

### 5.2 「回复消息」语义与降级定义（PR-18 细化）

| 项 | 定义 |
|---|---|
| 入口位置 | **消息中心抽屉**内（普通消息形态与流程通知形态均评估；实际仅流程通知形态可用，见下） |
| 回复语义 | 回复 = **回写为关联流程的一条审批意见**（写入该流程的审批历史，等同在流程里追加一条评论） |
| 触发条件 | **仅当该消息能定位到流程实例**时提供回复入口（依赖 PR-08 的消息↔流程关联） |
| **降级定义（结论）** | **无法关联到流程实例的消息 —— 不提供回复入口**（回复按钮隐藏/置灰并提示「该消息无关联流程，暂不支持回复」）。理由：①回复的唯一语义锚点是流程审批意见，无流程则语义落空；②避免引入「纯站内私信」这一全新能力域，控制本轮范围；③普通消息已有「标为已读」等既有动作，交互不至残缺 |
| 回写落点 | 流程审批历史表 `wf_history` 追加一条记录（`instance_id` + `node_code` + `operator_id/name` + `operation`（建议新增如 `COMMENT`）+ `comment=回复正文` + `created_at`）；`ProcessShell` 的「审批历史」区即自动展示 |
| 呈现位置 | 回复内容在**流程详情「审批信息/审批历史」区**可见（与 PR-05 抽屉三区呼应）；同时在消息抽屉回复区**就地回显**本条回复 |
| 依赖关系 | **PR-18 → 强依赖 PR-08**（消息↔流程实例关联）。PR-08 未落地则 PR-18 不可用 |
| 动作性质 | 回复**不改变流程状态、不推进节点**，仅追加意见（与「同意/驳回/转办」是不同性质的动作，互不干扰） |

## 9. 给架构师的关键约束（影响设计）

1. **单页多 Tab 优先**：门户三 Tab 若不新增路由，可完全规避 `keep-alive-outlet.tsx` 的 `PAGE_MAP`（精确匹配）/`DYNAMIC_PAGES`（前缀+`/`结尾）/`useParams` 恒空/详情页需冻结 pathname 等约束；抽屉建议为**临时态不入 URL**（对应 Q6）。
2. **去左栏实现点**：`app-layout.tsx` 的 `<aside>` 需按 `location.pathname` 条件渲染（仅 `/portal` 隐藏）；注意 `navNodes`/`activeAppCode` 逻辑不受影响。
3. **抽屉复用与改写**：消息抽屉已有成熟范式（`inbox-page.tsx:266-326`）；**流程详情抽屉需 `ProcessShell` 的紧凑/嵌入形态**——现 `ProcessShell` 是**整页组件**（含 `PageHeader` + 底部审批栏），直接塞进抽屉需拆分或加 `embedded` 变体。
4. **消息↔实例关联（P0 后端）**：`MessageItem` 缺 `instanceId/businessKey`；`ProcessService.notify(...)`（`ProcessService.java:458-469`）发出的通知 **`referenceTaskId=null`**，无任何实例线索 → 需新增关联字段 + 迁移，并在 `notify` 写入实例线索，接口透出。**该关联同时是 PR-07（通知看表单）与 PR-18（回复回写审批意见）的共同前置**。
5. **搜索需后端支持**：`/tasks/my`、`/tasks/handled`、`/workflow/instances/my` 三处**均无 keyword 参数**，PR-04 依赖后端新增模糊查询；消息搜索 `GET /messages/search` 已具备可复用。
6. **状态数据源差异**：六类子 Tab 背后是**三个不同接口**（`/tasks/my` 状态族、`/workflow/instances/my`、`/tasks/handled`），字段结构不同（`TaskItem` vs `WfInstance`）——聚合视图需**抽象统一列表模型或分 Tab 各自渲染**。
7. **详情定位方式**：待办项 `instanceId` 需经 `wfInstanceId(item)` 从 `sys_task.metadata`（脏 JSON）解析；无实例的待办应降级处理（现状回落 `/task/my-processed`）。
8. **PR-18 回复回写的目标表/字段（猜测，待架构确认）**：建议写入 **`wf_history`**（`WfHistory.java`，字段 `instance_id`/`node_code`/`operator_id`/`operator_name`/`operation`/`comment`/`created_at`）——以 `instanceId`（来自 PR-08 的关联）+ 当前节点 + 操作人 + 新增 op（如 `COMMENT`，现常量仅 `SUBMIT/APPROVE/REJECT/FORWARD/SKIP`）+ `comment=回复正文` 追加一条记录，`ProcessShell` 审批历史区即自动可见。**备选**：若需「回复」独立于审批历史展示，则另建 `wf_comment` 表——由架构师定夺。
9. **PR-18 净增端点**：后端 `MessageController`（taskflow）现仅 `publish/inbox/search/detail/read/stats`，前端 `messages.ts` 无写接口 → 需新增「回复」端点（前端 → BFF → taskflow），并透出「消息是否可回复」（即是否关联流程实例）的判定字段供前端控制入口显隐。
10. **抽屉内待办动作的接口差异（PR-12）**：`同意/驳回` 走 `ProcessShell` 用的 `POST /workflow/tasks/{id}/complete`（或 `POST /tasks/{id}/handle`），`转办` 走 `POST /tasks/{id}/transfer`（`TaskService.transferTask`：改处理人+置回 PENDING+补发通知）——**两个端点操作对象不同**（wfTask vs sysTask），抽屉内需按动作正确路由，勿混用。
