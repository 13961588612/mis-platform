## 0. 项目信息

- **Language**：简体中文
- **Programming Language**：前端沿用现有栈 `Vite + React + MUI + Tailwind CSS`；后端沿用现有 `mis-iam` / `mis-admin-bff`（Java 栈）；无需引入新框架
- **Project Name**：`user_mgmt_redesign`
- **原始需求复述**（已冻结，逐条确认）：
  1. **所属 APP 与编辑守卫**：新建必选「所属 APP」（前端原无此框，BFF 原取登录态 appId）；编辑若改所属 APP 且该用户已分配任意角色，则禁止保存（角色按 appId 隔离）。
  2. **新建/编辑表单改造**：字段顺序改为 所属APP→手机→姓名→邮箱→用户名→密码；删除底部「角色」复选框；按 `user.force.employee.bind` 显示「绑定员工」提示与按钮；强制模式下仅 所属APP/用户名/密码 可录入其余灰化、选员工自动回填；已绑定员工时编辑仅用户名可改、其余随员工同步；非强制模式编辑提供「解绑当前员工」。
  3. **查询条件**：增加「用户所属 APP」多选（支持跨 APP 查询）。
  4. **权限设置弹窗**：组织/部门/角色 分为三 TAB；取消组织↔部门联动（各自列出全部）；角色 TAB 承接表单删除的角色分配。
- **已确认决策**（D1–D4，本文不改动）：
  - **D1** 员工绑定唯一性：每个 APP 内 `employeeId` 唯一（新增 `existsByTenantIdAndAppIdAndEmployeeId`，选员工时即校验）。
  - **D2** 跨 APP 管理：全部登录用户都可跨 APP 查询/新建用户（实现不再加额外权限闸门）。
  - **D3** 角色分配落点：删除表单底部角色框，角色统一在权限弹窗「角色」TAB 分配。
  - **D4** 唯一性约束：用户名=租户+APP 内唯一（现状已实现，冲突抛 `USER_EXISTS(40901)`）；**手机也要求=租户+APP 内唯一（新增约束）**，新增 `existsByTenantIdAndAppIdAndPhone` / `...AndIdNot`，仅手机号非空时校验；两类冲突前端通用 toast 已有，并需按错误码把红字挂到对应字段（40901→用户名框，手机重复码→手机号框）。

## 1. 产品目标

对 MIS 平台用户管理模块进行一次以「APP 归属清晰化、员工绑定可控化、角色分配集中化」为核心的交互与约束重构：在不引入额外权限闸门（D2）的前提下，让新建/编辑流程显式绑定所属 APP、按系统参数强制或可选地绑定员工并自动同步其信息、将组织/部门/角色授权收敛到统一的三 TAB 弹窗，并对用户名与手机号在「租户 + APP」维度建立唯一性守卫与字段级错误提示，从而消除当前「APP 隐式取登录态、角色散落在表单、组织部门强联动」带来的数据错配与维护风险。

## 2. 用户故事

> 角色：**平台管理员**（主要操作者）、**普通运维**（按 D2 同样具备跨 APP 查询/新建能力）。
> 场景覆盖：**新建 / 编辑 / 查询 / 授权** 四类。

### 2.1 新建场景

**US-1（平台管理员 / 新建 — 所属 APP 与字段顺序）**
> As a 平台管理员，I want 在新建用户时先选择「所属 APP」并按新顺序填写字段，so that 用户被正确归属到 APP 且角色隔离不被破坏。

- **验收标准**
  - AC1：新建表单顶部出现「所属 APP」必选下拉框，保存时 `appId` 显式写入（不再取登录态）。
  - AC2：字段自上而下顺序严格为 所属APP → 手机号码 → 姓名 → 邮箱 → 用户名 → 密码。
  - AC3：表单底部原「角色」复选框已移除。

**US-2（平台管理员 / 新建 — 强制绑定员工）**
> As a 平台管理员，当系统要求用户必须是员工时，I want 通过弹窗选择员工并自动回填信息，so that 员工数据单一来源、避免重复录入。

- **验收标准**
  - AC1：若 `user.force.employee.bind=true`，表单提示「当前系统要求用户必须是员工」并出现「绑定员工」按钮。
  - AC2：仅「所属 APP / 用户名 / 密码」可录入，其余字段灰化。
  - AC3：点击「绑定员工」弹员工选择窗；选员工时即校验该 APP 内 `employeeId` 唯一（冲突即时提示不可选/不可保存）。
  - AC4：选中员工后自动回填 手机号、姓名、邮箱；未选员工时禁止保存。
  - AC5：保存时写入员工关联信息及「员工绑定」标记。

### 2.2 编辑场景

**US-3（平台管理员 / 编辑 — 改 APP 守卫）**
> As a 平台管理员，当编辑用户修改所属 APP 且该用户已分配角色时，I want 系统阻止保存，so that 因角色按 appId 隔离导致的角色失效被预防。

- **验收标准**
  - AC1：编辑时若修改了「所属 APP」且该用户已分配任意角色，保存被拒绝并给出明确提示（"已分配角色，禁止修改所属 APP"）。
  - AC2：未分配角色时允许修改所属 APP 并保存。
  - AC3：现行 `role.appId == user.appId` 硬校验保持不变，守卫文案统一表述为「已分配任何角色则禁止改 APP」。
  - AC4：守卫拒绝时后端返回 `VALIDATION_ERROR(40001)`，前端红字挂「所属 APP」框并伴 toast（与 D1 不冲突，跨 APP 换绑合法，见 Q4/Q8 裁决）。

**US-4（平台管理员 / 编辑 — 已绑定员工）**
> As a 平台管理员，当编辑已绑定员工用户时，I want 仅能修改用户名、其余信息随员工同步，so that 用户与员工信息保持一致。

- **验收标准**
  - AC1：已绑定员工时，编辑界面仅「用户名」可修改；手机号/姓名/邮箱只读并随员工变更自动同步（含邮箱）。
  - AC2：用户名唯一性（租户+APP）与手机号唯一性（租户+APP）仍在此界面受 D4 约束并提示。

**US-5（普通运维 / 编辑 — 解绑员工）**
> As a 普通运维，当系统未强制绑定员工时，I want 在编辑界面看到「解绑当前员工」按钮，so that 我可以解除用户与员工的绑定。

- **验收标准**
  - AC1：未配置 `user.force.employee.bind` 时，编辑界面提供「解绑当前员工」按钮。
  - AC2：已配置强制绑定时，该按钮不出现。

### 2.3 查询场景

**US-6（普通运维 / 查询 — 跨 APP 多选）**
> As a 普通运维，I want 按「用户所属 APP」多选条件筛选用户（支持跨 APP），so that 我可以跨应用管理用户。

- **验收标准**
  - AC1：用户列表查询区新增「用户所属 APP」多选条件。
  - AC2：支持同时选择多个 APP 进行跨 APP 查询。
  - AC3：按 D2，跨 APP 查询/新建不再额外加权限闸门（所有登录用户可用）。

### 2.4 授权场景

**US-7（平台管理员 / 授权 — 三 TAB 弹窗）**
> As a 平台管理员，I want 在权限弹窗中通过「组织 / 部门 / 角色」三个 TAB 分配权限，so that 角色分配集中且组织部门可独立勾选。

- **验收标准**
  - AC1：权限弹窗分「组织」「部门」「角色」三个 TAB。
  - AC2：组织与部门取消联动——各自根据权限列出全部组织、全部部门供勾选。
  - AC3：角色 TAB 承接表单删除的角色分配，为角色赋值的唯一入口（D3）。
  - AC4：保存将组织/部门/角色选择落库。

**US-8（平台管理员 / 保存 — 唯一性字段提示）**
> As a 平台管理员，当保存时用户名或手机号在租户+APP 内冲突，I want 红字精确挂在对应字段，so that 我知道该改哪个字段。

- **验收标准**
  - AC1：返回 `USER_EXISTS(40901)` 时，红字挂在「用户名」框并伴随 toast。
  - AC2：返回手机重复码时，红字挂在「手机号」框并伴随 toast。
  - AC3：通用 toast 通道（`onSave` catch → `toast.error`）保持可用。
