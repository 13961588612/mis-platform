# 增量 PRD：岗位类型管理界面 + 组织穿透

> 版本：v1.0（2026-08-13） | 作者：Alice（PM）
> 类型：简单 PRD（增量，不含竞品分析）
> 范围：本 PRD 仅覆盖两个已拍板需求；部门页「岗位编制」硬编码样例（EMPLOYEE_ASSIGNMENTS）为既有遗留，不在本迭代范围。

---

## 1. 项目信息

- **Language**：中文
- **Programming Language**：Vite + React + MUI + Tailwind CSS（默认，沿用现有前端栈）
- **Project Name**：`post_type_mgmt_and_org_pierce`
- **原始需求复述**：
  1. `sys_post_type` 表已有种子数据（5 类：管理/技术/财务/行政/运营，id 1-5），但无管理界面。用户拍板：**在岗位管理菜单内做子 Tab**，不新建独立菜单；岗位表单的类型下拉从真实数据读取。
  2. 一个租户下多个组织存在上下级关系（如总部/分公司），但 `sys_org` 无 `parent_id`（当前平级）。用户拍板三个决策：
     - **立项完整开发**；
     - **部门天然归属组织**（沿用 `sys_dept.org_id` 语义，非共享引用多对多）——穿透 = 汇总某组织及其全部子组织的顶级部门树；
     - 部门浏览界面加「组织穿透」选项：**只读**下钻展示子组织部门；**只能看不能修改，必须切换组织才能修改部门**；
     - 「对应组织的部门 = 该组织默认顶级部门（is_root=1），从这个顶级部门下钻」。

---

## 2. 产品定义

### 2.1 产品目标（三个正交目标）

1. **岗位类型可维护**：管理员在岗位管理内维护 `sys_post_type`（增删改查 + 启停 + 排序），岗位表单的类型下拉与类型数据实时同源。
2. **组织层级化**：组织支持上下级关系（`parent_id`），组织管理以树形/上级字段表达层级，并保证层级合法性（无环路）。
3. **组织穿透只读浏览**：部门浏览界面一键下钻「当前组织 + 全部子组织」的顶级部门树合集，只读可展开，修改必须切换组织。

### 2.2 用户故事

- 作为**系统管理员**，我能在岗位管理页维护岗位类型（例如新增「销售」类），保存后新岗位表单的类型下拉能选到它。
- 作为**系统管理员**，我删除一个已被岗位引用的岗位类型时，系统明确拦截并告知影响，避免岗位数据悬空。
- 作为**集团管理员**，我能在组织管理里把「华东分公司」设为「总部」的子组织，并看到清晰的上下级关系。
- 作为**集团管理员**，我在部门浏览页开启「组织穿透」，直接看到总部 + 各分公司的部门树；想看某分公司部门细节时，切换组织到该分公司再编辑。
- 作为**集团管理员**，我在穿透视图误操作时不会出现任何新增/编辑/删除入口，杜绝误改。

## 3. 技术规范

### 3.1 现状核实（已采信，作为设计输入）

- **sys_org**（V1 L57-73）：`id/tenant_id/code/name/sort/status/remark/deleted` 等，**无 parent_id**。接口：BFF `GET/POST/PUT/DELETE /api/v1/orgs*` → internal `GET /internal/v1/orgs、/names、/{id}、POST、PUT、DELETE`（mis-org OrgController）。前端 `org-list-page.tsx` 平级表格 + 表单。
- **sys_dept**（V1 L87-105）：`id/tenant_id/org_id(NOT NULL)/parent_id(默认0)/code/name/category_id/ancestors/sort/status/is_root(默认0)/leader_employee_id/deleted`；部门已天然归属组织且 `is_root` 标记顶级部门。接口：BFF `GET /api/v1/depts/tree?orgId=`、`GET /{id}`、`POST`、`PUT`、`DELETE`（→ internal `/internal/v1/depts/tree/{orgId}`、`/{id}/subtree-ids`、`/{id}`、`/{id}/staffing`、`POST/PUT/DELETE`）。前端 `dept-tree-page.tsx`：选组织 → 部门树 + 增删改。
- **sys_post_type**（V1 L114-124）：表存在；V39 种子 id 1-5。现有端点仅 `GET /api/v1/post-types`（BFF）+ `GET /internal/v1/post-types`（mis-org PostController），**无 CRUD 写端点**。前端 `AdminListPage`（`/system/post`）已通过 `postTypeOptionsLoader` 读真实类型下拉。
- **权限段位**：V39 用到 sys_api 91178-91194 / code 00900084-00900100 / sys_menu_api 91268-91283。**新迁移从 V40 起**；新增菜单/权限码需从最新段位顺延（架构师实现时核实精确区间）。

### 3.3 UI 设计稿（文字/结构描述，非真实设计稿）

**① 岗位管理页子 Tab 结构**

```
岗位管理（/system/post）
├─ [岗位列表] [岗位类型]          ← 子 Tab（复用页面级 segmented control 样式，参考部门页视图切换）
│
├─ Tab1 岗位列表 = 现有岗位表格 + 筛选 + 新建（保持不变）
└─ Tab2 岗位类型 =
   ├─ 表格列：编码 | 名称 | 排序 | 状态(启用/禁用) | 引用岗位数(建议) | 操作
   ├─ 操作：新增 / 编辑 / 删除（被引用时按钮禁用或点击拦截提示）
   └─ 新增/编辑 Sheet：编码* | 名称* | 排序 | 状态(switch)
```

**② 组织管理页树形 + 上级字段**

```
组织管理（/system/org）
├─ 树形表格（或列表 + 「上级组织」列）：根组织(上级=—) → 子组织缩进
├─ 新增/编辑 Sheet 增加字段：「上级组织」树形下拉（默认无/顶级；排除自身及子孙）
└─ 删除：若存在子组织/部门 → 拦截提示（按 Q&A④）
```

**③ 部门页穿透开关 + 穿透视图**

```
部门管理（/system/dept）
├─ 视图切换：[组织架构] [岗位编制] [组织穿透]   ← 新增第三项
├─ 组织选择器：穿透模式下仍可选「根组织」（更换组织 → 退出穿透，见 P0-PR-05）
├─ 组织架构（现有）：选组织 → 该组织部门树 + 新增/编辑/删除
└─ 组织穿透（新增）：
   ├─ 标题提示：「只读浏览：总部及全部子组织的部门树；修改请切换组织」
   ├─ 树内容：orgA 顶级部门树(完整子树) / orgB 顶级部门树(完整子树) …（并列 forest）
   ├─ 无新增/编辑/删除/子部门按钮
   └─ 行可展开查看下级部门
```

### 3.4 待确认问题（Q&A）

| # | 问题 | 建议默认（供架构师/用户确认） |
|---|---|---|
| ① | 组织穿透只读边界：仅部门 CRUD 只读？「岗位编制」视图是否也在穿透下隐藏/只读？ | 建议：穿透仅针对部门树浏览；「岗位编制」为独立视图（当前本就只读、且为遗留样例数据），穿透模式下不渲染编制入口，避免混淆 |
| ② | 组织层级深度是否硬限制？ | 建议 ≤3 层（集团/公司/部门）；不硬限制（仅校验环路），UI 层提示最佳实践 |
| ③ | 岗位类型删除被引用时：硬拦截还是软删停用？ | 建议**硬拦截**（删除报错 + 提示引用岗位数）；若需保留历史类型，可改为「置为停用」 |
| ④ | 组织删除时其子组织/部门如何处理？ | 建议**拦截**：存在子组织或部门时禁止删除，提示先迁移/删除下级；不做级联删除 |
| ⑤ | 穿透视图是否需要显示「来自哪个组织」标识？ | 建议**显示**（每棵顶级树挂组织名徽标），信息成本低、可读性收益高 |
| ⑥ | 岗位类型做「组织维度」还是全局共享？ | 建议**全局共享**（与 `sys_post_type` 无 org_id 的现状一致，租户内一套类型）；不引入组织维度 |
| ⑦ | 穿透后部门下拉（如员工任职选部门）是否也需要穿透？ | 建议**本期不做**：穿透仅为浏览诉求；任职/岗位等选择类下拉保持单组织语义（避免跨组织误任职）；列入后续迭代候选 |

### 3.5 接口/权限影响提示（供架构师核实，非最终设计）

- 岗位类型需新增写端点：BFF `POST/PUT/DELETE /api/v1/post-types*` → internal `POST/PUT/DELETE /internal/v1/post-types*`（mis-org PostController/Service 扩展）。
- 组织层级需扩展：org 实体/表 `parent_id`；列表返回含 `parentId`（或新增树端点）；写请求支持 `parentId`。
- 穿透需新增只读端点：`GET /internal/v1/depts/pierce?orgId=X`（建议）+ BFF `GET /api/v1/depts/pierce?orgId=X`；返回 forest（多棵顶级部门树，含来源组织标识）。
- 新增接口需登记 `sys_api` / `sys_menu_api` / 权限码（V40 起，从最新段位顺延）；岗位类型 CRUD 建议新增按钮级权限码或复用 `system:post:*`（架构师定）。

## 4. 验收标准（可验证）

1. 岗位管理页出现「岗位列表 / 岗位类型」两个子 Tab；岗位类型 Tab 显示 5 条种子数据（管理/技术/财务/行政/运营）。
2. 在岗位类型 Tab 新增「销售」（code 如 `sales`）后：类型列表出现该行；切到岗位列表新增岗位，类型下拉可选到「销售」。
3. 删除未被引用的类型（如新建的「销售」）成功；删除被引用类型（如「管理」）被拦截并提示引用岗位数。
4. 组织管理中可将「华东分公司」的上级设为「总部」；保存后列表/树形显示层级；将某组织设为自身或子孙的上级被拒绝并提示。
5. 删除存在子组织或部门的组织被拦截（按 Q&A④ 最终决策）。
6. 「总部」下挂「华东分公司」后，部门页开启组织穿透：能看到总部顶级部门 + 华东分公司顶级部门（含子树），页面无新增/编辑/删除/子部门按钮。
7. 穿透视图下展开子部门正常；切换组织选择器后退出穿透，回到该组织普通视图且恢复编辑按钮。
8. 后端穿透端点仅支持 GET；直接调用写端点（POST/PUT/DELETE depts）不因穿透模式改变既有行为（穿透本身不提供写路径）。
