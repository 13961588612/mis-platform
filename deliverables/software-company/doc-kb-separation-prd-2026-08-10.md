## 2. 现状调研要点（可复用 / 需新建）

### 2.1 可复用（存量资产，勿重复造）

| 资产 | 位置 | 现状 | 复用点 |
|---|---|---|---|
| 树形分类表 | `kb_category`（KbCategory：parent_id/enabled/sort/remark） | 后端已支持多级 parent_id；**前端仅渲染两级**（`kb-category-page.tsx` flattenCategories 只做根→子） | 知识库分类树直接复用；前端加深渲染即可 |
| 库级 ACL | `kb_acl`（KbAcl：subject_type=user/role/dept、action=read/manage/acl） | 主体 id 复用 mis-iam/mis-org，不建本地用户表；`KbAclService` CRUD + `KbVisibilityService` 判定 | 授权主体模型、判定链可直接扩展为「节点级」 |
| 可见性判定 | `KbVisibilityService`（visible = {public ∧ enabled} ∪ {ACL grant} − disabled） | `resolveGrantedLibraryIds` 按 user∪role∪dept 取并集；部门多挂已支持；**不做部门树向上继承**（显式勾选子部门） | 作为知识库域数据权限的基座 |
| 主体取数客户端 | `KbSubjectClient` | 从 mis-iam 拉角色/部门 id，未配置降级空 | 文档库域同样需要 |
| IAM 菜单 RBAC | `sys_menu / sys_api / sys_role_permission / sys_user_role`，权限码如 `kb:library:list`、`kb:acl:grant` | 功能可用性由菜单/按钮权限码门控；内置 `TENANT_ADMIN`（type=1, data_scope=1）+ 自定义角色（type=2） | 功能级权限保持 RBAC 不变 |
| 数据范围枚举 | `sys_role.data_scope`：1 全部/2 本部门/3 本部门及下级/4 仅本人/5 自定义/6 本组织（字典 `sys_data_scope`） | 面向组织数据；`RoleDataScopeVO(dataScope, orgIds, deptIds)` | 借鉴「数据范围」心智，但**树节点范围是本项目新语义**，不复用 orgIds 字段 |
| 文件级切片 | `kb_document` V23 三列（chunk_method/chunk_token_num/separator） | 已落地库级默认 + 文件级覆盖 | 文档库域文档可继承此配置形态 |

### 2.2 需新建（核心差距）

| 差距 | 说明 |
|---|---|
| **文档库域整体缺失** | 现 `kb_document` 直接归属 `kb_library`，无「原始文档资产」独立域、无独立分类树、无独立权限 |
| **ACL 是库级，非树节点级** | `kb_acl` 只有 `library_id`，没有 category 维度；「任意层级管理员 + 子树继承」必须新增节点资源授权模型 |
| **无跨域引用** | 知识库文档与文档库文档无引用关系表；需新建引用（或迁移语义） |
| **分类树前端仅两级** | 后端已支持多级，前端渲染与交互需加深到任意层级 |
| **文档级权限** | `kb_document` 无独立 owner/ACL；「管理员可管理其下级的目录内文档」隐含文档需能定位到分类节点 |

### 2.3 与现有权限体系的关系结论

- **功能权限（能否用某个按钮/页面）**：沿用现有菜单 RBAC（权限码），本项目**不新建角色类型**；
- **数据权限（能看/能管哪些资源）**：新建「树节点资源 + 节点管理员授权表」承载「任意层级管理员」语义，属 **RBAC 之上的一层资源授权（扩展）**，与现有 `kb_acl` 同构（复用 subject_type/subject_id/action），只是把粒度从「库」下沉/上提到「分类节点」；
- **判定链**：先功能权限码（菜单）→ 再资源授权（节点/子树）→ 最后引擎侧文档可见性过滤（RAG 检索）。

## 3. 产品目标

1. **双域分离**：将「原始文档资产（文档库）」与「RAG 检索问答（知识库）」拆为两个独立管理域，各自拥有独立分类树、独立权限模型、独立生命周期，解决当前「文档只能挂在一个知识库下、无法独立治理」的结构性限制。
2. **分级治理**：两个域的树形分类均支持在任意节点设置管理员，管理员可管理**以该节点为根的子树**内的目录结构与文档，形成「根管理员 → 域管理员 → 节点管理员」的分级授权体系。
3. **一处维护、多处复用**：知识库通过「引用」从文档库选文档（而非复制），文档库维护一份原文，多知识库复用；检索范围同时受「引用关系」与「文档可见性权限」双重约束。

## 4. 用户故事

| # | 角色 | 场景 | 价值 |
|---|---|---|---|
| US-1 | 平台/租户管理员 | 在文档库域创建「制度/合同/技术」等多级分类树，为每个根分类指定一名部门负责人作管理员 | 分级授权，避免全平台管理员成为唯一管理入口 |
| US-2 | 节点管理员（如「技术文档」分类管理员） | 登录后默认看到自己管辖的子树，可在此子树下新建/调整子目录、上传/停用/删除文档，但看不到其他节点内容 | 权责对等，管理员只对自己分管范围负责 |
| US-3 | 普通用户 | 按被授权的分类节点访问文档库，只能浏览/下载自己有 read 权限的文档 | 数据安全，越权不可见 |
| US-4 | 知识库管理员 | 在知识库域创建分类树，并为「产品知识库」节点设置管理员 | 知识库域同样分级治理 |
| US-5 | 知识库管理员 | 创建知识库时从文档库树中选择若干文档（多选，含按目录批量选），建立引用；文档库更新文档后，知识库可选择同步或保持快照 | 一处维护、多处复用，避免重复上传 |
| US-6 | 节点管理员 | 上级节点管理员将其管辖的某子节点移交给其他管理员，或回收授权 | 组织调整时可平滑交接 |
| US-7 | 审计/合规人员 | 查看某节点下谁有管理权、授权记录、文档变更历史 | 可追溯、合规 |

## 6. 权限模型草案（重点：任意层级管理员最小可行方案）

### 6.1 核心思路

**不新建第二套 RBAC，而是「RBAC 之上加一层树资源授权」**：现有菜单权限码负责「能不能用功能」，新增「节点授权表」负责「能管/能看哪些节点子树」。

### 6.2 数据模型（建议）

```
doc_category（文档库分类树，新建，结构与 kb_category 同构）
  id, parent_id, name, enabled, sort, remark, created_at, updated_at

doc_category_admin（文档库节点管理员授权表，新建）
  id, category_id, subject_type(user|role|dept), subject_id, created_at, updated_at
  -- 语义：该主体是该节点管理员，管理范围=以该节点为根的子树
  -- 可选：action 固定为 manage（管理子树目录+文档）；若需读权限另建 doc_category_acl 或复用本表加 action

kb_category_admin（知识库节点管理员授权表，新建；或将 kb_acl 泛化为 category 维度）
  id, category_id, subject_type, subject_id, created_at, updated_at

doc_document（文档库文档表，新建；或复用 kb_document 迁移）
  id, category_id, title, owner, secrecy, status, version, size, format,
  engine_document_ref, chunk_method, chunk_token_num, separator, created_at, updated_at

kb_library_document_ref（知识库引用文档库文档，新建）
  id, library_id, doc_id, ref_mode(reference|snapshot), ref_status(active|disabled|broken),
  created_at, updated_at
```

### 6.3 权限判定链（最小可行）

```
hasManageCategory(user, nodeId):
  1) user 为 superadmin / TENANT_ADMIN（或拥有域级管理权限码如 doc:admin）→ true（全局管理员）
  2) 沿 nodeId → 祖先链逐级查 doc_category_admin（subject ∈ user ∪ user.roles ∪ user.depts）→ 命中即 true（节点管理员 + 祖先继承）
  3) 其余 false

resolveVisibleCategoryIds(user):
  = 所有「命中的管理员节点」的子树节点 ∪ 显式 ACL 授权节点（若做文档级权限则追加）

文档操作校验：
  文档所在 category_id 的 hasManageCategory == true 才可上传/停用/删除/改切片；
  读权限由 doc_category_acl 或密级（public=全员读）裁定，沿用 KbVisibilityService 口径。
```

### 6.4 与现有 RBAC 的关系

| 维度 | 现有（保留） | 新增 |
|---|---|---|
| 功能可用性 | 菜单/按钮权限码（`kb:library:edit`、`doc:document:edit` 等） | — |
| 数据范围 | `sys_role.data_scope`（组织向） | 树节点授权表（资源向，本项目主体） |
| 授权主体 | user/role/dept（mis-iam/mis-org 复用） | 同左，不建本地用户表 |
| 判定位置 | BFF UserPermissionLoader（功能码）+ mis-kb KbVisibilityService（库可见性） | 新建 NodeAdminResolver（mis-kb 或新模块）供两域复用 |
| 角色映射 | `TENANT_ADMIN`=全局管理员；自定义角色按菜单授权 | 节点管理员是「授权行」，不是角色；普通角色+节点授权即可成为某子树管理员 |

### 6.5 关键取舍（写入口径）

- **子树继承用「祖先链查询」而非「物化子树授权行」**：避免增删节点时同步改大量授权行；节点数规模（千级以内）祖先链深度可控。
- **删除节点策略**：沿用 `KB_CATEGORY_HAS_CHILDREN`——先删子/迁子再删节点，避免孤儿授权；迁移子节点时授权默认跟随（父管理员仍能管），可后续再做「授权随迁」细化。
- **不做部门树向上继承**（与现有 `KbVisibilityService` 口径一致）：授权给「研发部」不自动覆盖子部门，前端部门选择器树形多选显式勾选。
- **功能权限码仍先行**：节点管理员能管子树，但若角色未配「文档上传」按钮权限码，仍不能执行该操作（双闸门）；文案上需向用户说明「授权管子树 ≠ 获得全部功能按钮」。

## 9. 竞品参考（一句话对齐心智）

- **语雀**：知识库=文档库一体，目录树多级，团队/成员按空间授权——本项目差异点是「文档库与知识库解耦 + RAG」；
- **Confluence**：Space（空间）级权限 + 页面级限制，父子页面继承——对应「节点管理员 + 子树继承」心智；
- **飞书知识库**：知识空间/分类树 + 空间管理员，文档从云文档引用——对应「跨域引用 + 引用同步」心智；
- **Notion**：页面树天然层级 + 权限按页面/子页面授予——对应「任意节点授权 + 子树范围」心智。
