### 1.1 原始需求复述（增量）

针对 2026-08-10 企业级充分性评审结论「检索核心调参够用、企业治理维度不足」，正式立项一期，覆盖四项：

1. **P0 · 操作审计（等保合规硬性）**：KB 全部写操作（库设置/切片/模型/检索参数修改、文档删除/启停/重解析、分类管理、同义词词表变更等）留痕「谁、何时、做了什么、关键参数前后值」。
2. **P1-a · 解析治理可视化**：库/文档列表透出解析进度（引擎 progress）、失败原因（parse_error），提供失败重试入口。
3. **P1-b · OCR 与切片 overlap**：切片区新增 OCR 开关 + OCR 语言 + chunk overlap（重叠）参数，对齐引擎 parser_config 能力。
4. **P1-c · 简单检索过滤**：命中测试页与检索链路支持按文档/时间范围过滤；密级限定列为候选。

## 2. 产品定义

### 2.1 产品目标（三条正交）

1. **合规可审计**：KB 任何写操作可追溯——操作人、时间、动作、关键参数前后值一次查清，满足等保 2.0 三级审计要求（对应 P0）。
2. **解析可治理**：解析进度、失败原因、失败重试全部可视化，把「静默丢失的文档」变成「可定位、可恢复的资源」（对应 P1-a/b）。
3. **检索可聚焦**：命中测试与检索链路支持按文档/时间范围收敛，让调参与排障从「全库大海捞针」变为「圈定范围对比」（对应 P1-c）。

### 2.2 用户故事

> 编号风格对齐既有 PRD（角色字母 + 序号 + 需求池编号）；本期前缀 KE（KB Enterprise）避免与已交付 PRD 的 US-A1/B1 撞号。

#### 知识管理员（admin）

- **US-KE-A1（KE-01）**：As a 知识管理员，I want 我修改库设置/切片/文档状态等任何写操作都被记录（含修改前后值），so that 合规审计有据可查、误操作可定位可回滚。
- **US-KE-A2（KE-03/04/05）**：As a 知识管理员，I want 在文档列表看到每个文档的解析进度与失败原因，并对失败文档一键重试，so that 不翻服务日志就能定位和恢复解析失败。
- **US-KE-A3（KE-06/07）**：As a 知识管理员，I want 在切片设置里开启 OCR（选语言）并调整切片重叠，so that 扫描件/图片型 PDF 可被解析、相邻片段上下文不因切分而割裂。
- **US-KE-A4（KE-08/09）**：As a 知识管理员，I want 在命中测试时只针对某几份文档或某时间范围内上传的文档做检索，so that 我能验证「某文档的新版本为什么没被召回」而不被全库噪声干扰。

#### 运维（ops）

- **US-KE-O1（KE-01/02）**：As a 运维，I want 在操作日志页按「知识库」模块筛选全部 KB 写操作并查看入参明细，so that 排障与合规取数一个入口完成。
- **US-KE-O2（KE-03/04）**：As a 运维，I want 在库维度看到解析失败文档清单与失败原因统计，so that 能批量判断是引擎配置问题还是单文件问题。

#### 业务方（business）

- **US-KE-B1（KE-03/04/05）**：As a 业务方，I want 上传文档后能看到解析进度、失败时知道原因并点「重试」，so that 不用等管理员介入就能确认文档可被检索。

### P1-a（解析治理可视化）

| 编号 | 需求 | 验收要点（可度量） |
|---|---|---|
| **KE-03** | **解析进度透出**：库/文档列表展示每份文档的解析进度（百分比，来自引擎 progress，0~100%）。pending 显示「待解析」、parsing 显示百分比、success 显示「已完成」、failed 显示「失败」。解析中/待解析文档列表**必须**自动刷新进度（轮询或复用引擎对账节奏，实现方式架构师定）。 | ① 文档列表出现「解析进度」列，parsing 状态显示百分比数字（如 67%）；② 触发重解析后进度从低到高变化并最终到 100%；③ pending 不显示 0% 而显示「待解析」文案。 |
| **KE-04** | **失败原因透出**：`kb_document` 新增可空 `parse_error` 文本列（技术债 11.1 候选方案），记录最近一次解析失败原因（引擎错误摘要，截断到合理长度）；解析成功/重解析时清空。文档列表对 failed 文档展示失败原因（行内气泡或详情），库维度提供失败文档筛选。 | ① 造一个解析失败文档：列表可见 failed 状态与失败原因文案；② 重试成功后 `parse_error` 清空、状态转 success/parsing；③ 失败原因来源为引擎侧错误信息（RAGFlow `progress_msg` 优先），不展示内部堆栈。 |
| **KE-05** | **失败重试入口**：文档行内对 failed 文档提供「重试」按钮（复用现有单文档重解析链路）；库级提供「重试全部失败文档」入口（可对 reparse-all 扩展 failed-only 过滤，实现方式架构师定）。重试后状态转 parsing，失败原因清空。 | ① failed 文档行内出现「重试」，点击后状态转 parsing 且 parse_error 清空；② 库级入口仅对 failed 文档触发重解析，success/pending 文档不受影响；③ 重试动作产生审计日志（见 KE-01）。 |

### P1-b（OCR 与切片 overlap）

| 编号 | 需求 | 验收要点（可度量） |
|---|---|---|
| **KE-06** | **OCR 开关与 OCR 语言**：切片设置区新增「OCR 识别」开关（默认关）与「OCR 语言」下拉（中文/英文/中英混合等，选项以引擎实测能力为准）；开启后对扫描件/图片型 PDF 走 OCR 解析。该配置**必须**下发引擎 parser_config；修改后提示重解析才生效（沿用既有「改切片须重解析」引导）。 | ① 开关关闭时 OCR 语言下拉灰化；② 开启后保存、重进回显一致；③ 开启后上传扫描件 PDF 可被解析出文本并可检索命中；④ 修改后出现「需重解析」引导。 |
| **KE-07** | **切片重叠（chunk overlap）**：切片设置区新增「重叠长度（token）」参数（正整数，默认引擎默认值/0，上限以引擎能力为准）；相邻切片保留重叠上下文，降低切分割裂。**必须**与库级/文件级切片合并语义一致（文件级覆盖库级）。 | ① 参数可保存回显；② 下发引擎 parser_config 后实际切片出现重叠（以引擎返回 chunk 内容/接口为准）；③ 未设置时行为与现状一致；④ 修改后出现「需重解析」引导。 |

## 5. 权限与审计要求

### 5.1 权限码（对齐平台既有 `kb:xxx` 体系）

| 功能 | 权限码 | 说明 |
|---|---|---|
| 审计查询 | `log:list`（既有） | 监控-操作日志页既有权限，本期不新增 |
| 文档重试 / 重试全部失败 | `kb:document:edit`（既有） | 复用文档编辑权限；重试属文档管理写操作 |
| RAG 设置（含 OCR/overlap） | `kb:library:edit`（既有） | 复用库设置权限 |
| 命中测试过滤 | `kb:hittest:run`（既有） | 过滤为命中测试参数，不新增权限 |
| 解析失败文档查看 | `kb:document:edit` / 列表既有可见性 | 文档列表权限不变，仅增列 |

> 本期**不新增权限码**——四项功能全部挂在既有 `kb:*` 权限与文档可见性之上，避免权限矩阵膨胀。若架构师发现 RAG 设置端点实际未挂 `kb:library:edit` 门禁，需在技术设计中一并校正（关联技术债 11.2 sys_api 登记，见 Q5）。

### 5.2 审计要求（等保对齐）

1. **写操作全量留痕**：§3.1 未挂清单全部补 `@OperLog`，写端点一律 `recordParams = true`。
2. **关键参数前后值**：P0 验收强制「前后值」；实现机制由架构师裁决（Q2），产品口径：**必须含修改前值与修改后值**，且不因采集失败阻断业务。
3. **脱敏红线**：补挂 `recordParams=true` 前必须确认该端点入参无凭据类字段（模型名/切片参数等均非密钥）；**技术债 11.5（审计脱敏对分隔符命名不生效）与本期补挂行为强相关**，建议随本期一并销账（Q6，见 §8 风险）。
4. **审计自身健壮性**：审计写失败不影响业务（既有语义）；审计表保留期沿用平台策略。

## 6. 非功能需求

1. **解析状态同步成本**：解析进度轮询不得对引擎造成压力——复用既有 `syncOpenParseStatuses` 节奏（仅 pending/parsing 文档查询），进度列随状态同步批次更新即可；不做逐文档高频轮询。
2. **parse_error 长度**：截断存储（建议 ≤ 500 字符），避免引擎错误信息膨胀表体。
3. **检索过滤降级**：`metadataFilterSupported=false`（noop）时 UI 置灰 + 明确提示，绝不静默忽略（对齐 WA-06「前端置灰 + 后端强制 + 降级提示」三道防线口径）。
4. **兼容**：`RagSettings` 新增 OCR/overlap 字段沿用「追加末位 + 零 DDL + `withDefaults()` 兜底」模式；存量 JSON 缺字段行为与现状一致。
5. **性能**：审计采集为 AOP 旁路，不阻塞主链路；过滤条件为检索期参数，不增加额外引擎调用（时间范围过滤的本地化实现方式架构师定，见 Q7）。

## 9. 关键风险（回传主理人）

1. **审计补挂面大（P0 主风险）**：§3.1 一次性补挂 18+ 写端点 `@OperLog(recordParams=true)`，需逐端点确认入参无凭据字段；且**前后值能力是现有切面没有的**，实现方案（Q2）未定前验收口径需与架构师对齐，避免「记了但不含前值」返工。
2. **OCR/overlap 键名依赖引擎实测（P1-b 阻塞点）**：T00 只实锤了 `chunk_token_num`/`delimiter` 白名单与「parser_config 未知键 code:102 严格拒绝」。若 RAGFlow 实例不支持 OCR/overlap 键，本期只能「落库 + UI 回显 + 提示暂不生效」，验收用例需预置该降级路径。
3. **审计脱敏盲区（技术债 11.5）与补挂强相关**：补挂 `recordParams=true` 扩大审计入参采集面，分隔符形态的敏感键（如 `access_key`）若出现将明文入审计表——建议 Q6 随期销账，否则等保审计自身成为数据泄露面。
4. **权限门控与审计不同步（技术债 11.2/11.3）**：审计补挂不等于 API 层有权限码门控（`deny-unmapped=false`）。若本期只补审计不登记 `sys_api`，「有审计无门禁」的合规叙事不完整——建议 Q5 至少把补挂端点一并登记。
