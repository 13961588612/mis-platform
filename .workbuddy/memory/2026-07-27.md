## 抽取返回空 fields 根因定位 + BFF 修复（BugFix）
- 现象：「用户管理」4 个 AI 入口已浮现（前序 B 方案改造生效），但点「智能录入/抽取」返回 `{"fields":{},"confidence":null,"unmapped":[]}`。
- 用户疑问：是否需要开发 AI skills？**结论：不需要。**
- 根因（已核实）：ai-platform `mis-extract` agent 不依赖 skill（`skill_dirs=[]` 正常，靠 system prompt 让 LLM 直接输出 JSON）。LLM 实际抽对了（uvicorn 日志印证 `assistant_text` 含完整正确 JSON，如 `realName:"小王"`），但外层裹了 ```` ```json ```` 围栏。BFF `AiCapabilityTranslator.parseExtract/parseSummary/parseRag` 直接用 `objectMapper.readTree(data.getResponse())`，遇围栏抛 `JsonParseException` 被 `catch` 静默吞掉 → 返回默认空值。

## 领域模型整体规划评审（架构师高见远）
- 用户假设：「module 下级是 api；module 无租户；app 有租户；app 下菜单/按钮与 api 关联」。结论：**基本成立，1 处心智模型需修正 + 2 处 P1 补强**。
- 判定：① module→api 归属存在，但 module=跨租户平台级静态服务目录标签（无 tenant_id/app_id），api 真正挂在 `(tenant,app)` 下、用 `module_id` 标微服务；② module 确无 tenant（sys_module 表无 tenant_id 列，ADR 有意为之）；③ app 有 tenant_id（sys_app.tenant_id NOT NULL）；④ 菜单/按钮=`sys_menu`(type=3 按钮)→经 `sys_menu_api` 关联 `sys_api`。
- 关键缺口 R1(P1)：`sys_module` 表存在但**全 Java 代码 0 实体/Repository/DTO**，且 `sys_api.module_id` **无外键**（V1-V7 全库 0 个 FK）。module 仅由迁移/种子 SQL 维护（V2/V6），管理后台不可 CRUD。要做「长期规划容器」须实体化 + 加 FK 或应用层校验。
- 风险 R2(P1)：菜单无 `module_id`，按钮→module 需经 `sys_menu_api→sys_api→module`（多值），规划需固化此回溯路径。
- 风险 R3(P2)：tenant 降维（tenant_id 冗余在 app/menu/api/user/role，均非空无 FK）——经典单库行级隔离，合理但需写护栏 `子表.tenant_id == app.tenant_id`；注意 `tenant_id DEFAULT 1`/`dict DEFAULT 0` 哨兵语义。
- 风险 R4(P2)：按钮=`SysMenu.type=3`+`permission`+`sys_role_permission(perm_type=menu)` 清晰，但 type 是裸 Integer（SysApi.type 却是枚举），建议 `MenuType` 枚举对齐。R5：`SysApp` 在 mis-iam/mis-auth 双实体漂移。R6：角色只能授权到菜单/按钮节点、api 经继承，无直授权 api。
- 待用户确认：module 是否要后台 CRUD？「module 下级是 api」准确语义？按钮是否要直接 module_id？哨兵租户语义？是否接受角色不直授权 api？

## 领域模型修订版规划（基于用户 3 答答复）

- 迁移 P1：V8 `drop_api_tenant_app_and_add_module_fk.sql` — `ALTER sys_api DROP tenant_id/app_id`、`uk_api_app_code`→`uk_api_module_code`、`ADD FK module_id→sys_module(id)`。种子数据 tenant/app 恒为 1，去重平凡。
