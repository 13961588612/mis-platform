## Agent 多副本横向扩展方案研究（团队 software-agent-lease-scale）
- **问题确认**：现有 agent 租约 `aip:agent:{agentId}:owner` 是单 owner 独占——`core_ownership.py` 的 `CLAIM_SCRIPT` Lua 强制「他主拒绝」，且 `manager.py` 的 `sync_from_configs` 在 claim 失败即 `continue` 不起运行时。只解决「跨 agentId 分片」与「单 agentId 故障转移(HA)」，**未横向扩展并发**：热点 agentId 流量再大也只有 1 个实例在扛。
- **核心张力**：并发单位实为 session，不是 agent 进程。现有代码已支持跨会话并行（core 内 `Semaphore`+每消息 `create_task`）与同会话串行（`aip:session:{sid}:lock` 分布式锁）；瓶颈只是「同一 agentId 的所有 session 被单 owner core 独占消费」。
- **产出文档**：`docs/ai-fusion/agent-multi-replica-scaling.md`（架构师高见远）。对比方案 A 分片流 / B 副本池+会话亲和 / C 共享消费组 / D 租约副本配额 / E 动态扩缩。推荐 **方案 C（共享消费组 + 活跃副本池）**：同一 `agentId` 的 `aip:stream:agent:{agentId}` 保持单流单组 `agent-core-group`，N 副本 core 作为同组消费者竞争消费；复用现有 session 锁 + XAUTOCLAIM；出站 `aip:stream:gw:{gwId}:events` 零改动、零新中间件；仅放宽 `core_ownership.py`/`manager.py`/`inbound_worker.py` 的单 owner 门控。

## 概念澄清 + 核实派工（13:28）
- **软亲和 vs 硬亲和（用户混淆点）**：`replica = f(sessionId, agentId)`（如 `hash(sessionId)%N`）是两者共用的**偏好函数**。区别在副本故障行为——**硬亲和(B)**=强制走 f()、副本挂则该会话切片 unavailable 需显式 rehash/drain；**软亲和(C+)**=偏好走 f()、副本挂则 XAUTOCLAIM 自动接管。用户说的「sessionId+agentId→确定实例」是硬亲和的算法，不是软亲和。软亲和还需 `sessionId→preferredReplica` hint 才有粘性。
- **软亲和不"解决"无状态重放限制**：它把「每轮必须重放」降级为「仅副本故障时才重放」——正常路径同会话粘同副本、插件态在 RAM 无需重放；故障接管路径才需从 Redis 重放，此时插件态未外置的限制照样成立。根上消除需在故障接管时也能忠实重放（外置上下文工程工作态）。软亲和是桥，外置是根治。
- **已派工程师(software-engineer，后台，团队 software-agent-ctx-verify)** 核实上下文工程插件层外置：①插件选择/中途切换是否落 Redis/PG；②RAG/memory/压缩派生产物是否外置；③checkpoint saver 类型(MemorySaver vs 持久化)；④插件态可序列化性。待返回后钉死 纯C/C+软亲和/硬B 的风险边界。
