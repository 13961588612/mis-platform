- **架构师结论：推荐方案 A（独立工程 + 微服务嵌入）**，核心依据：
  1. 同构先例：mis-kb、agent/ai-platform 均为独立工程经 Gateway 接入
  2. 技术栈根本冲突：recon=MyBatis+Oracle 平台库+MySQL 业务库只读 vs MIS=JPA+PG 单库（ADR-015/001），B 方案需推翻两项 ADR
  3. 数据隔离：Oracle 平台库+MySQL 源库只读是领域刚需，迁 PG 无意义
  4. 前端两阶段：外包管理后台可独立先行，并入门户列为二期
- **方案 A 落地要点**：独立 repo（recon-plat 目录即新工程根）、包名按 MIS 规范改 com.mis.recon、Gateway 加 `/api/v1/recon/**` 路由直连（不经 BFF，与 mis-kb/agent 一致）、平台库 Oracle 保留、MIS 侧配合=路由+Nacos 配置+mis-iam APP/权限码登记+（二期）门户菜单
- **B 方案冲突清单（不推荐）**：双 ORM 并存、多数据源 vs Flyway 单库、动态数据源 vs JPA 事务、包名规范、数据权限自建、外包前端重写为 React 六项
- **二次评审（用户纠偏"技术栈未锁定"后）**：推荐 **方案A（独立 recon-service）× 技术栈跟随 MIS（Spring Data JPA + PostgreSQL）**。核心：①平台库=PG 独立 database `recon`（可同集群），独立 Flyway 迁移集含 QRTZ_*；②引擎热路径=JdbcTemplate + 原生 SQL（PG `ON CONFLICT` 批量 upsert、PG 序列 + recon_seq_watermark 水位表），JPA 只承担配置/查询侧；③多源只读=动态 DataSource 注册表 + JdbcTemplate（源库无实体，ORM 不适用，MyBatis 动态 SQL 也非必需）；④per-check=TransactionTemplate REQUIRES_NEW + 每 check 结束 clear EntityManager；⑤Quartz 走自身 JDBC JobStore 不经 JPA，无冲突；⑥ADR-015/007/011 沿用，ADR-001 靠 recon 独立库守住 MIS 单库精神；⑦前端并入 mis-admin-web 复用外包原型页面、九宫格入口（Gateway+BFF 聚合，先例 agent/ai-platform）
