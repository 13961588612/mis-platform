## 知识库二期 Wave A（团队 software-kb-phase2-wave-a，进行中）
### 权限体系关键事实（本轮实测核实，长期有效）
- **`uk_menu_app_permission`**（`V1__init_schema.sql:269-270`）：`sys_menu (app_id, permission) WHERE status=1 AND permission IS NOT NULL` 部分唯一索引。**同一 app 下一个权限码只能挂一个菜单行**，「页面节点 + 按钮节点共用同一 permission」的常见写法在本仓库会直接迁移失败。应用层 `MenuService.java:98-100` 亦有 `existsByAppIdAndPermissionAndStatus` 校验，语义一致：一码一功能。
- **权限码聚合不过滤菜单类型**：`mis-system/.../service/MenuService.java:79-88` `permissionCodes()` = `findByIdInAndStatus(menuIds,1) → getPermission → filter(hasText)`，**不看 type**。即页面节点（type=2）自带 permission 就能供前端 `hasPermission()` 使用，按钮节点（type=3）不是必需品。
- **API 鉴权注册表不过滤菜单类型**：`mis-system/.../repository/SysApiRepository.java:44-58` `findRegistryRows()` = `sys_api JOIN sys_menu_api JOIN sys_menu JOIN sys_module`，只过滤 `a.type='api' / a.status=1 / m.status=1`，**不过滤 m.type**；`sys_menu_api`（V1:294-302）也只有 menu_id/api_id 无类型约束。**故 sys_menu_api 可以直接挂页面菜单节点**。
- **authOnly 陷阱（易踩）**：`ApiPermissionRegistry.java:69-73` —— permission 为空即判 authOnly；`ApiPermissionInterceptor.java:72-73` 对 authOnly **直接 return true 放行**。所以「把挂载菜单行的 permission 置 NULL 来绕开唯一索引」= 把该 API 降级成登录即可调，是隐蔽的越权口子。同理 `application.yml:48 deny-unmapped: false` 时未登记路径一律放行（Interceptor:52-57，且在取 LoginUser 之前）。
- **结论沉淀**：新增「页面 + 按钮」权限迁移时，正确姿势是**只在页面节点写 permission，sys_menu_api 挂页面节点**；不要建同码按钮节点，也不要用 NULL permission 的按钮节点当挂载点。

## mis-kb 权限与 role 对接关系（用户提问，已查证代码）
- **结论**：mis-kb 的访问权限**确实与 role 对接**，且是「用户 ∪ 角色 ∪ 部门」三类主体并集授权（`KbVisibilityService.resolveGrantedLibraryIds`）。
- 机制：`KbAcl.subject_type ∈ {user, role, dept}`（SubjectType 枚举）；角色级授权经 `KbSubjectClient.fetchUserRoleIds(userId)` 调 mis-iam `GET /internal/v1/users/{id}` 取用户角色 id 列表，再匹配 `kb_acl`；KB 不建本地角色表，`subject_id` 复用 mis-iam 角色 id。
- **两个 role 别混**：① `kb_acl.subject_type='role'` 的授权主体 role（mis-iam 角色，接入权限）；② `KbQaMessage.role`/`QaRole`∈{user,assistant} 是问答消息发送者身份，与权限无关。
- **第三层闸**：平台级 API 鉴权（mis-system `ApiPermissionInterceptor` + sys_api 注册表 + `LoginUser` 权限码）是独立闸，控「能否调到 KB 端点」，用全局 MIS 权限码，不读 kb_acl。
- 历史坑 X-04：`KbSubjectClient` 原实现调错端点 + 角色 id/code 混淆 + id 类型错，角色级 ACL 曾恒失效，已修复（现调 `/internal/v1/users/{id}`，String→Long）。IAM 不可达降级仅 public 库可见（安全侧收紧）。
