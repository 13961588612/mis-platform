## 会话耗时条「检索」字段语义澄清(用户问 8.64s 是否太长)
- **结论**:截图 `检索 8.64s` 并非纯向量检索,而是**父 agent 委派 mis-rag worker 的整段 `latency_ms`**(intent=rag 的 DISPATCH_TRACE 累加,session_timing.py:132-148 的 `_dispatch_trace_latency_ms`)。worker 内部链路=`resolve_visible_libraries`(mis-kb 1 次)+ RAGFlow `/internal/v1/kb/rag/retrieve`(真正向量检索)+ LLM 生成 + `_persist` 顺序 3 次 mis-kb HTTP(qa_pipeline.py:718-740)。标签"检索"有误导。
- **各阶段之和 > total_ms 属正常**:5 阶段为各自独立测量的片段/上报值存在重叠(worker 委派 span 与父生成 span 交叠);只有 `total_ms` 是权威 wall-clock(session_timing.py:199 注释)。
- **优化抓手(尚未做)**:① mis-rag worker 内部加耗时拆分埋点(resolve_visible / RAGFlow_retrieve / worker_generate / persist)方能判断"真正检索"是否慢;② `resolve_visible_libraries` 每次检索重查 mis-kb 可加 30-60s 缓存;③ `_persist` 3 次 mis-kb 调用顺序 await 可改 `asyncio.gather` 并行省 200-800ms。
- 用户未要求立即改造,仅澄清。待确认是否给 mis-rag 加内部计时埋点(快速模式,约 3-4 文件)。
