===== 任务4：权限落地真实有效性 —— 不通过【阻塞发布 P0-B，比工程师自报的更严重】 =====
【静态代码阅读 + grep，未起服务、未真的 curl。以下「会发生什么」是逐行读拦截器代码推断出的结论，不是实测。】

■ 结论一：KbController.java:355-356 的注释与事实不符，确认无疑。

注释原文声称「V17 已登记 POST /api/v1/kb/hit-test → kb:hittest:run」。事实：
  - `grep -ln "INSERT INTO sys_api"` 在整个 migration 目录只命中 V2、V4、V5、V6 四个文件，V12-V17 一个都没有
  - `grep -n "/api/v1/kb" *.sql` → **零命中**。整个 KB 模块没有任何一个 API 登记进 sys_api
  - V17 自己只碰了两张表：sys_menu 和 sys_role_permission，通篇没有 sys_api
所以这条注释是纯粹的事实错误。而且是最坏的一类错误：它让后来的维护者相信 API 层已有防护，从而不会去加代码级判权。定时炸弹的说法不夸张。

■ 结论二：拦截器不是「拦不住」，是「连看都不看就放行」。

ApiPermissionInterceptor.java:52-58：
    Optional<Match> match = registry.match(request.getMethod(), path);
    if (match.isEmpty()) {
        if (properties.isDenyUnmapped()) {
            throw new BusinessException(ResultCode.FORBIDDEN, "接口未授权映射");
        }
        return true;          // ← 未映射直接放行
    }
关键就在 denyUnmapped 的取值。我查了：
  - ApiPermissionProperties.java:12 → `private boolean denyUnmapped = false;`（默认 false）
  - 全仓 `grep -rn "deny-unmapped|denyUnmapped|api-permission"` 扫所有 *.yml / *.yaml / *.properties（含 deploy/nacos-config 下 test / integration / prod 三套）→ **零命中，没有任何环境覆盖这个默认值**
即 denyUnmapped 在所有环境都是 false → hit-test 请求走到第 57 行 `return true` → 判权逻辑（第 76-87 行）根本没被执行。

还有一处比工程师描述的更糟：第 57 行的 return 发生在第 66-70 行 LoginUser 判空**之前**。也就是说对未映射路径，这个拦截器连「是否已登录」都不校验。登录态实际由上游网关 + GatewayContextFilter 头透传承担（GatewayContextFilter 只是 `LoginUserHeaderResolver.resolve` 后写入上下文，resolve 不到就什么都不做，本身不拒绝请求）。

■ 结论三：兜底 ACL 到底兜住了什么、漏了什么。

KbHitTestService.java:96-99 调 visibilityService.hasPermission(userId, libraryId, READ)。
KbVisibilityService.java:152-167 的实现：
    152  public boolean hasPermission(Long userId, Long libraryId, String action) {
    153      if (userId == null || libraryId == null || action == null) {
    154          return false;                       ← 兜住了：无身份头的匿名请求
    155      }
    156      if (AclAction.READ.code().equals(action)) {
    157          KbLibrary lib = libraryRepository.findById(libraryId).orElse(null);
    159          if (lib != null
    160                  && Secrecy.isPublic(lib.getSecrecy())
    161                  && lib.getStatus() != null
    162                  && LibraryStatus.isEnabled(lib.getStatus())) {
    163              return true;                    ← 公开库无条件放行，不查任何 ACL 授权
    164          }
    165      }
    166      return resolveGrantedLibraryIds(userId, action).contains(libraryId);
    167  }

兜住了：
  - 匿名/无 X-User-Id 的请求（userId 为 null → false）。QaInternalController.currentUserId():128-129 在无 LoginUser 时返回 null，链路一致。这是唯一真正生效的兜底。
  - 非公开密级库（内部/秘密/机密）：仍需显式 ACL 授权，第 166 行查得到才放行。这层是实的。

没兜住：
  - **第 156-164 行对 public 密级 + 启用状态的库无条件返回 true，完全跳过 ACL 表。**

■ 你问的那个具体问题：无 kb:hittest:run 但有某库读权限的用户，直接 curl POST /api/v1/kb/hit-test 会怎样？

答：**完全跑通，返回 200 + chunk 原文。** 拦截器放行（未映射），ACL 查到显式授权也放行，一路无阻。

而且实际暴露面比你设的这个前提还大一圈：**连「某个库的读权限」都不需要。任何能通过网关拿到登录态的用户 —— 哪怕在 kb_acl 表里一条授权都没有 —— 都能对任意「public 密级且启用」的知识库跑命中测试，直接读出 chunk 原文。** 因为第 156-164 行对公开库根本不看授权表。

这与设计文档验收项 A4（第 1360 行）「无 kb:hittest:run 的用户看不到菜单、直接访问被拦、直接调 API 返 403」直接冲突。静态分析结论是返 200，A4 不成立。

顺带一个实现与设计的偏差：设计文档第 44 行的架构图画的是
    KbController ── @Permission("kb:hittest:run") ──▶ KbFacadeService
但实际代码 KbController.java:367-368 只有 @PostMapping 和 @OperLog，没有 @Permission。我进一步查了全仓：`find -name "Permission.java" / "RequiresPermission*.java"` 无结果，`grep "@Permission("` 无结果 —— **这个注解机制在仓库里根本不存在**。所以设计图画的是一个不存在的东西，工程师也没法照着实现。这个偏差建议同步反馈给架构师（按纪律我不直接联系他，走你中转）。
