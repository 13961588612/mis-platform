# 总控路由（所有问数请求先过这里）

## 0. 执行环境与调用契约（硬约束，S1~S7 共用）

本组 Skill 运行在**百购分析智能体（Worker）**下，取数链路为：

```
百购 Worker（本组 Skill）→ iqd__ask 工具 → iqd 编排层 → WrenAI → Doris
```

| # | 约束 | 为什么 / 违反后果 |
|---|------|------|
| 1 | **只通过 `iqd__ask` 工具取数** | 禁止直连 WrenAI 的 HTTP 接口、禁止直连数据库。本层也无权改写 SQL |
| 2 | **必须显式传 `connection_id=bg-data`**（问数项目配置里的项目名，也可传该项目的数字 id） | 缺省时 iqd 回落到平台默认连接 → **查错库**。项目名匹配不到或同名多条时工具直接报错，不会改查别的库 |
| 3 | `question` 传改写后的**规范问句** | 纪律口径见下方注 |
| 4 | **禁止解析或校验 SQL** | `view=user` 下 iqd 的 `ResponseProjector` 已删除 `sql` / `sql_dialect` 键，本层**拿不到 SQL**，一切基于 SQL 的校验都不成立 |
| 5 | **禁止委派其他智能体** | Worker `max_depth=1`，不可再 spawn 任何 Agent（含知识问答）。所需背景知识必须由 Coordinator 经 TaskBrief 注入 |
| 6 | **多轮追问传 `thread_id`** | 追问链（S5-C → S5-D 等）靠它透传上下文，不得依赖用户复述 |

> **注（口径对齐，务必理解后再落地）**：`iqd__ask` 工具描述原文写「question 必须传用户原始问题原文，不得改写」。
> 本组 Skill 的价值恰恰是「补全槽位 + 术语规范化 → 生成规范问句」，二者不冲突：
> **改的是表达形式，不改的是语义**。平台侧已将工具描述精确化为「不改变语义」；
> 若线上仍是旧措辞，属平台侧待办项，不影响本组 Skill 承担改写职责。

### 0.7 改写问句会被谁消费（这一节决定改写该怎么写）

> **"我又不访问 WrenAI，改写还有用吗"** —— 有用，而且比想象中更有效。
> iqd 拿到 `question` 后**不改写、不重写**（`orchestrator.py` 全程 `question=request.question` 原样传递），
> 原样用于三处，**其中两处发生在 iqd 内部、跟 WrenAI 无关**：

| 消费方 | 代码位置 | 对改写的要求 |
|---|---|---|
| ① 喂 WrenAI 生成 SQL | `nl2sql.generate(question=request.question, ...)` | 语义清晰、槽位齐全 |
| ② 召回历史相似样本 | `recall_queries(question=question.strip())` | **格式必须与样本库一致**，否则召回率下降 |
| ③ 候选表打分排序 | `_rank_model_candidates(question=...)` | **必须保留中文业务词**，见警告一 |

**警告一：不要把中文业务词改成英文列名。** `_rank_model_candidates` 靠中文关键词给候选表打分，
内置映射只有这几个：

```
销售 → sale/sales/gmv/trd/order    门店 → store/shop/spm
订单 → order/ord/trd               客户 → customer/cust/user/member
成本 → cost                        季度/上季 → day/date/ord_date
```

若把「卖了多少钱」改写成 `sale_amt`，句中没有「销售」二字 → **别名全部丢失，选表打分退化**。

- ✅ `【S1】昨天 嘉兴店 销售金额`
- ❌ `【S1】2026-10-12 store=101 sale_amt`

**警告二：`【S#】` 前缀是否有用，取决于样本库格式。** 前缀对 WrenAI 生成 SQL 本身没有帮助，
它只对「② 召回样本」起作用：

- 若 `iqd_sql_pair` 里的样本 question **也是** `【S1】...` 格式 → 前缀有助于召回，**保留**；
- 若样本库是自然语言问法 → 前缀是噪音，**去掉**。

> **铁律：样本入库格式必须与本组改写模板同进同出。**
> 这条要在 Phase 1 导入样本时一并确认，并写进上线前置检查——两边不一致时，前缀会帮倒忙。

## 1. 处理流水线

```
用户提问
 → ①敏感词/越界检查（第5节）
 → ②分析型 vs 取数型分流（第4节）
 → ③Skill路由（第2节仲裁规则）
 → ④槽位检查（缺必填槽位→追问，禁瞎查）
 → ⑤问句改写为规范问句（带【S#】前缀，"不改变语义"纪律见第 0 节注）
 → ⑥调 iqd__ask 工具（必传 connection_id=bg-data；追问时传 thread_id）
      · iqd 侧依次完成：范围裁定 → 生成 SQL → 行级注入 → 血缘复核 → 执行 → 脱敏 → 投影
      · 越表/越权在 iqd 侧 fail-closed，本层无需也无法复核 SQL（第 0 节约束 4）
 → ⑦结果三层校验（第6节）
 → ⑧按Skill回答模板组织输出 + 追问建议
```

## 4. 三类分流（知识型 / 取数型 / 分析型）

- **知识型**（"什么是高端会员""流失周期怎么算的""会员管理制度"，不需要数字）→ **本路由不处理、不下 SQL**。
  受 Worker `max_depth=1` 限制（第 0 节约束 5），**本智能体不能委派知识问答智能体**。按序处理：
  ① 若本次 TaskBrief 中 Coordinator 已注入相关知识背景 → 直接引用并注明来源（这是推荐路径，
     由 Coordinator 先问知识问答、再把结论写进自包含的 TaskBrief）；
  ② 否则 → 答复「这是口径/制度类问题，建议向知识问答提问」，并原样保留用户问法便于其追问。
  **禁止**为了补背景自行编一段"我记得的制度"——那是编造，比答不上更糟。
- **取数型**（什么时候/多少/排名/占比/对比）→ 走WrenAI。
- **分析型**（为什么/怎么办/建议）→ 先取数，再按下面四层组织。禁止只查一个总数后直接给原因。禁止把原因写成已经证实的事实。
- 纯预测类（"下个月会涨吗"）→ 直接答复"当前不支持预测类问题"。

### 4.1 每次出数的四层（2026-10-17 已落稿）

缺一层就补查，或写明缺什么。不要用形容词填空。

1. **现状**：时间、范围、指标、数值，并声明所用列（默认含券 `sale_amt`；去券、去税另说）。
2. **趋势**：有 `_yoy` / `_mom` 或去年同期表才写升降。没有预计算列时写「本次没有同比列」，禁止编百分比，禁止自己做日期偏移。
3. **原因**：只拆有列可对的因子，每条标「待验证」。
4. **行动**：下一步看哪一张表或哪一个下钻。不编活动方案，不预测下月。

枚举取值未从库中回填前（见 `docs/ai-fusion/bgbh-analyst/第一步-枚举与问数范围.md`），原因层只用这些不依赖未签字存储值的拆法：

- 价、量、折扣：销售金额、件数、折扣率、去券金额。毛利率只用 `sale_gross_profit_rate`，不要重算。
- 结构：门店、厅房、品牌的排名。不要按经营模式的数字编码去过滤，该编码尚未签字。
- 客流三因子：客流、转化率、笔单价必须各有一次取数结果，才能说差额主要落在哪一项。缺一项就写缺。`sale_avg_price` 是件单价，不是客单价。
- 关联：写明分母是同品类还是全商场。没有 lift 列就不说「关联很强」。

这些先不要写成原因：新老会员过滤、高端区间过滤、考核流失当正式数、用开业时间剔除新店、把账面投入产出比说成发券增量。

## 5. 越界拒答清单（数据未覆盖，禁止硬查）

库存、采购、进货、线上电商订单（小程序/APP交易明细）、财务对账、客服客诉、员工绩效、超市业态数据、DWD明细自由查询（券核销逐笔、停车逐笔）。
**拒答话术**：「这个问题超出了当前数据范围（{具体原因}），我已记录并转交数据组评估。」

## 6. 结果三层校验

1. **空结果** → 先按时间口径降级重试一次（如"昨日"改"最近有数据的日期"，需声明）；仍空→"该条件下暂无数据"。
2. **量级异常** → 金额/人数超历史P99×3 → 回答前标注"结果存疑，请谨慎参考"并记录。
3. **越权 / 取数失败处理** → **本层不做 SQL 白名单校验**（拿不到 SQL，见第 0 节约束 4）。
   改为：收到 iqd 侧权限类错误（已知 **`45204`** = 越权或行级范围为空，fail-closed）→
   如实告知「无该数据权限」并建议联系数据管理员，**不重试、不换表重试**。
   真正的越表拦截在 iqd 侧 `iqd_scope_policy`（in_scope）+ 表级 ACL 硬执行。

## 7. 失败兜底

- 同一问题调 `iqd__ask` 两次失败 → 答复「这个问题暂时没查准，已记录问题原文转数据组」，落未命中日志。
- 本层日志字段：时间、用户原文、路由 Skill、改写后 question、connection_id、thread_id、失败原因、工具返回摘要。
  **用途是归因"路由与改写"环节是否出错**（如路由错 Skill、槽位漏补全）。
- **不要重复记 iqd 已有的账**：iqd 侧已全量写 `iqd_ask_log`（含 question、SQL、耗时、行数、状态），
  每周导出未命中问法补样本库时，以 `GET /api/v1/iqd/traces` 为准。
- **错误码现状**：目前明确可依赖的只有 **`45204`（越权/行级范围为空）**。其余工具错误的细粒度错误码
  待与平台方确认，在此之前统一按「如实报告工具返回的错误信息，**禁止编造数据**」处理。

## 8. 全局指令（真源在 iqd 侧 `iqd_knowledge`；本节为对照副本）

> **归属说明**：以下指令的最优落点是 iqd 侧的知识/术语表（`iqd_knowledge`，kind=instructions），
> 由 iqd 在每次取数时统一注入 WrenAI —— 这样即便调用方绕过本组 Skill（例如其他域直接调 `iqd__ask`）
> 口径依然成立，这也是唯一能防住"绕过 Skill 就口径失控"的做法。
> 本节保留为**对照副本**，用于对账与本地复核。
> **两边内容必须一致**，唯一真相源是《02_WrenAI语义规则》第 4 节；
> 若副本与 iqd 侧不一致，**以 iqd 侧为准，并立即回来同步本节**。

1. 时间默认：未指定→最近一个完整自然日(T-1)，回答中必须声明所用时间。
2. 聚合防重：ADS为预聚合表，禁止重复GROUP BY导致翻倍；人数用预计算cnt列。
3. 金额口径：默认sale_amt；"去券/净额"→sale_uncpn_amt；"去税"→sale_uncpn_taxout_amt。
4. 门店范围：未指定→全部门店合计；单店问题必须带store过滤。
5. 周期表：stats_period是过滤条件不是分组维度；"近一年"→stats_period对应枚举值，禁止自拼日期区间。
6. 同比/环比：优先用_yoy/_mom列或last_year表，禁止现场日期偏移计算。
